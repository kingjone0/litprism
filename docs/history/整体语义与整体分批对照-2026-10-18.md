## 为什么分批

“分块”是数据库中的带论文、物理页和稳定 ID 的证据片段；“分批”是一次模型请求装入哪些片段。分块必须保留，方便引用回溯；分批由本地预算决定，并非要求每篇论文固定分 4/6 批。

`reading_batches` 使用统一 Meter 估算完整 system/user 消息，扣除输出预留。能装下一次读取就一次提取；超出配置预算才按顺序分批，不用生成摘要替代后半篇原文。配置窗口不是服务商已验证的最大窗口。表格完整行装不下会拒绝，而非从列中间切开。

| 维度 | 一次提取 | 分批提取 |
|---|---|---|
| 全局上下文 | 同时看到可索引正文，较容易联系前后条件与局限 | 单批只看到局部，需另做全文陈述核查 |
| 信息取舍 | 共享一个输出额度，可能漏掉中段的具体结果 | 多个输出额度，较多细节，也容易重复、把局部主题当成全文问题 |
| 成本与失败 | 一次调用；过大或截断会影响整体 | 更多调用及重复指令；任一批可能格式损坏或语义失真 |
| 保证 | 不能保证理解正确或覆盖全部事实 | 片段全部送达也不能保证全局一致 |

长上下文的检索与问答可能存在位置效应，见原始研究 [Lost in the Middle](https://arxiv.org/abs/2307.03172)。它不是对当前 DeepSeek 服务的评测，不能用它推定本项目的准确率。

## 本轮实现

- 六个主解读字段、跨论文对比陈述进入独立机器核查。服务端分配陈述 ID，保留原陈述、批次和候选来源；核对对象、数值、单位、方向、条件、否定和归属。
- 支持结论必须有实际来源中的连续引句。只归一布局空白，不把上标/下标等 Unicode 字符替换成普通数值。引句存在仍不能数学上证明语义蕴含，状态明确称“机器支持”。
- 复核既按输入预算，也按每组最多 6 条约束输出规模。机器输出缺项、重复、伪造引句不放行。困惑度混用百分点的已知反例有确定性守卫。
- 原词数值索引只比较同来源论文、对象、指标、条件；不猜同义、换单位、把不同实验混成矛盾。模型提出的差异是待核查候选。
- 全文陈述分片两两核对，包含首尾等远距离批次；最多 16 次跨片调用。预算未覆盖、返回未知陈述 ID、传输失败等不会被标成整体通过。不是只检查相邻批，也不是再生成一段看似统一的摘要。
- 复核达到输出/推理上限时熔断，后续复核停止；候选及来源仍保留，整体完成标记为 false。跨片核查同样熔断。其他调用异常仍使任务失败，保留上一版解读。
- 待核对/机器发现不符/跨批差异相关陈述不进入正常六字段和对比正文、导出；右栏可看原陈述、理由、引句、差异双方和原文链接。
- 人工可修正正文、填写依据并单独入可信知识库，原始解读不被覆盖，论文真实性等级不改变。审核绑定完整解读版本哈希、陈述 ID；过期版本、已撤销来源不准确认。支持拒绝、撤销和历史记录。差异双方的候选原文随人工知识条目保存。
- schema v5 新增 semantic_runs / semantic_reviews。跨论文结果有不可变审核快照。没有主动打开或迁移用户主数据库；真实测试只读提供商配置与既有加密密钥。

范围限制：此轮语义核查覆盖六个主字段及跨论文对比，术语定义、普通 RAG 问答和 Skill 并未因此获得同等语义保证。旧解读不会自动补核，界面提示重新解读；mock/第三方未声明复核能力的模型明确标为未运行，不伪造机器通过。

## 冻结的真实对照

同一 GPT-3 arXiv v4，75 页，SHA256 `97fd272f1fdfc18677462d0292f5fbf26ca86b4d1b485c2dba03269b643a0e83`；同一解析器、290 块、同一模型 `deepseek/deepseek-v4.1-flash`、温度 0、输出预留 16384。来源为解析后的可索引原文；17 个未可靠恢复的表格区域仍明确待核对，不能称整个原始 PDF 无损进入模型。

原始请求记录：`_selftest.long-paper/semantic-whole-batched-live/`。不保存凭据或推理链正文。

| 仅首次提取，不含复核 | 整体（配置窗口 131072） | 分批（配置窗口 32768） |
|---|---:|---:|
| 提取请求 | 1 | 4 |
| 实际输入 token | 61601 | 63840 |
| 实际输出 token（含服务报告的推理） | 5715 | 30597 |
| 总 token | 67316 | 94437 |
| 请求耗时合计/秒 | 34.27 | 177.76 |

只做了一次独立生成，不是统计稳定性或准确率排名。分批这次更贵，不能声称分批省 token。

观察到的具体差异：

1. 整体关键结论保留了 PTB 20.50、新闻辨识约 52%、WiC 弱项与污染限定，但没有列出 SuperGLUE 71.8 的均值；第 2 批则明确提及该均值及与 BERT-Large 的比较。一次读取装得下也会取舍。
2. 整体局限覆盖失去连贯性、自相矛盾、物理常识、样本效率、接地、偏见等；分批第 1 批只能引用局部限制，第 3 批才包含正式局限章节。若直接拼接各批，很容易把“本批未见”当“全文没有”。
3. 第 4 批保留了附录所写 200B 与其他位置 175B 的原文差异说明，以及 Table C.1 随示例随机种子不同而略有差别的限定。它们应待查出处与条件，不能由合并器自动改成同一个数。
4. 第 3 批虽 HTTP/JSON 解析成功，却出现异常的巨长字段名、HTML 草稿碎片和缺失正常字段。它不能因为“调用成功”就被视为合格的科学解读。原始响应留档，机械检查与语义核查仍分别保留结果。

针对第 4 点，随后加入未知字段/结构损坏拒收守卫。`_selftest.long-paper/structural-revalidation.json` 是对冻结原始响应的离线重验：第 3 批全部主字段被阻止，其余三批通过机械检查。此前付费运行时记录的机械通过状态未被改写，不能把它当作新守卫的结果；新守卫没有再发提取请求。

## 服务端复核预算反例与验收边界

原始大组复核：整体和分批方案均发生 `OutputLimitError`，输出达到 16384，其中报告为推理的 token 耗尽/几乎耗尽额度。6 条小组复核也重现；独立 `reasoning_effort=low` 探针在 8192 上限仍返回 length。该参数只用于单次测试，没有改用户配置，也不据此推断所有模型都有同一问题。官方文档说明推理消耗输出预算：[DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。第三方转发与官方接口的参数行为不能直接等同。

最终运行 `semantic-budget-final-live` 复用此前提取结果：逐段校验原文、物理页和冻结 chunk ID，重建的完整提取消息必须逐字一致才允许复用；仅复核调用收费。复用计数与真实调用计数分开，失败记录不会冒充成功记录。

这轮已补齐可追溯的语义复核、差异候选和人工接管路径，**尚未通过当前真实服务的自动语义质量验收**。预算耗尽意味着未核完，不意味着论文存在矛盾，也不意味着所有候选错误。后续应先解决该模型/服务的有界结构化复核能力，并用真实反例验证，再扩大模型调用；不推进 F3。
