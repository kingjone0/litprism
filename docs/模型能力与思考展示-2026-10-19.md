# 模型能力数据与思考展示

> 本文记录已实现的能力接线，不规定复核必须全部交给模型。最新人工与可选全文批量辅助的修订目标及实际差距，见 [当前设计与功能流程图](当前设计与功能流程图.md)；本轮先做设计校对，不启动后续真实语义验收。

本轮按用户确认收口：保留 P 系列既有全文前缀、范围指令与分批回退，不重写输入规划、陈述配额或语义裁决。当前短论文的重点是后续复核，不是继续扩展容量控制。

## 能力数据

2026-10-19 对公开的 [Command Code 模型目录](https://api.commandcode.ai/provider/v1/models) 做了一次只读 GET，没有读取密钥或发送生成请求。`deepseek/deepseek-v4.1-flash` 返回：

```json
{
  "id": "deepseek/deepseek-v4.1-flash",
  "context_length": 1000000,
  "supported_endpoints": ["/chat/completions", "/responses"]
}
```

该次返回没有最大输出字段。上下文 1M 可由 API 读取，最大输出 384K 使用用户确认值；本项目按十进制记录为 1,000,000 / 384,000 token。这是能力配置与目录观察，不是已经实际生成 384K 的证明。

原模型列表只保留 ID/名称，遗漏了 `context_length`，现已补齐。获取可用模型时保存能力缓存和更新时间；缓存按服务商和模型隔离，修改启用状态或显示名不会丢失缓存。API 有明确字段时优先采用；缺失字段回落到已确认默认值，再到已有能力数据。未知不凭名称猜成服务承诺。

能力只有只读展示，不提供窗口、最大输出、任务输出额度或输出预留的编辑控件。保留提供商地址、协议、密钥及模型目录管理。服务暂时不可达时不为读取能力阻断本地启动，使用已有数据；已有数据不意味着刚完成一次联网刷新。

## 输出与复核

已知能力的桌面调用在发送完整消息前统一计算：

```text
输出额度 = min(模型最大输出, 上下文窗口 - 完整输入估算 - 估算余量)
估算余量 = max(256 token, 输入估算的 5%)
```

当前短论文通常直接得到 384K 额度；额度不是要求生成的长度，实际输出量按服务上报计。没有用户任务上限，不要求手工调整 `max_tokens` 或输出预留，旧配置写入接口拒绝这类修改。输入估算仍不是模型精确 tokenizer。

提取、问答、逐项语义复核和差异复核共用发送端逻辑。自动路径不再被旧的 4096/8192 或 `LITPRISM_REVIEW_MAX_TOKENS` 限制；模型能力未知的旧入口和显式历史实验仍保留原兼容行为，不能概括为所有 CLI/MCP 已完成同等接线。

严格 JSON、来源白名单、审核状态、复核请求次数、失败保留待审与显式恢复要求不变。多次调用降低单次负担，但仍检查服务返回的 `length` / `max_tokens` 截断；不将不完整响应发布为正常结论。当前 Flash 默认等待由旧 120 秒提升至 300 秒；连接等待和读取等待仍区分。

N01 持久记录各次实际额度、输入估算及模式，刷新后可查看。模型能力、参数或实现改变仍拒绝精确复用旧运行。schema v8 新增能力缓存及调用参数记录；本轮没有打开或迁移用户主库。

N02 新建实验默认 `model-capacity`：1M / 384K，发送时自动分配。旧 baseline/thinking 档只用于复现实验，原结果不重新解释为使用了新能力；原固定样本质量门槛不变。

## 思考展示

OpenAI 兼容协议接收独立 `reasoning_content`，Anthropic 接收 `thinking` 内容块。聊天在回复完成后提供折叠区，刷新仍可查看；未返回独立字段时不虚构思考过程。尚非逐 token 流式显示。

思考以转义纯文本展示，与答案、来源链接分开，明确未经核验。只存在会话元数据中，不进入后续轮次的证据、引用校验或可信知识。N01 日志不保存思考原文，只记录数值参数和用量。

## 验证边界

完整隔离回归 831 passed；API/UI 无窗口流程覆盖只读能力数据、思考折叠/刷新/转义、来源与人工审核/撤销、持久运行、主题和窄屏。真实联网只检查了公开模型目录，未追加生成调用；不能据此宣称真实整篇复核已经通过。N02 原失败与 N03 来源续接问题仍见原验收记录。

## 复核侧接线（2026-10-19 第二轮）

输出额度先接了能力数据，**输入侧的复核协议此前没有接**：`MAX_REVIEW_INPUT = 6000`、分组条件
`len(current) >= 1`（每次一条），与 1M 窗口是两套东西。

本轮改法（仅 `semantics.review_units`）：

- 能力已知（`automatic_output` 且 `model_window_tokens` 存在）时，单次可用输入按窗口的 80% 计算；
- 逐条复核消息复用提取阶段的同一份全文序列化（`reading.excerpt_text`）作为**前缀**，陈述清单放在尾部，
  才**有机会**命中前缀缓存（是否命中仍以服务上报为准）；
- 批量大小由内容与窗口决定，不写死条数；
- 全文前缀自身装不下时退回候选片段模式，不截断原文冒充已核；
- 能力未知的旧入口保持原样（每次一条、6000 上限），CLI/MCP 等未接线入口行为不变。

零成本测量（合成数据，stub 模型只计数）：

| 陈述数 | 旧入口（能力未知） | 能力模式（1M 窗口） |
|---|---|---|
| 240 | 240 次调用（每次 1 条） | **1 次调用（240 条同批）** |

新增回归：`tests/test_semantics.py` 三条（一次核完多条、前缀复用且在陈述之前、前缀装不下时退回）。
完整回归 **833 passed / 1 skipped**。

### 差异层同轮接线

### 真实样例全流程实测（2026-10-19）

fastText v3（5 页 / 22 块，SHA256 `6cbcf62…`），真实提供方，隔离库，`tools/live_full_pipeline.py`。

| 场景 | 能力路径 | 调用 | token | 耗时 | 结果 |
|---|---|---|---|---|---|
| 复核开启 | **未解析**（legacy） | 78（复核 40） | 121,850 | 737s | 40 条：39 支持 / 1 不符 |
| 复核开启 | **1M / 384K** | **7（复核 1）** | **37,053** | 147s | 25 条：23 支持 / 2 待审 |
| 复核关闭 | 1M / 384K | **1** | **12,370** | 35s | 25 条候选、`skipped_by_user` |
| 复核关闭 | 未解析（legacy） | 6 | 64,662 | 218s | 52 条候选 |

- 候选与复核结果 **ID 完全一致**（`ids_match=true`），人工确认两轮各生成一条 `manual_confirmed` 知识条目。
- 关闭复核时不产生任何语义调用，正文保留原始提取。

**踩到的坑与修正（2026-10-19 已修）**：

1. 自建 `LLMConfig` 会把 `automatic_output`/窗口丢掉 → 请求回到 8192 并被截断。
   新入口必须复用 `apply_active_window` 解析后的 `cfg.llm`（工具脚本已按此改）。
2. 没有生效模型时原先静默回落 `32000`。现在：
   - **强制选模**：真实模型入口（`build_llm`）在未选模型时返回 400「尚未选择模型」；
     离线 `mock` 仍可用。`apply_active_window(..., require_active=True)` 同样直接报错。
   - **能力优先级**：API 实测 > 库里存的 > 用户确认白名单 > 提供商级。
     白名单只在前两者都缺时兜底，不再掩盖"没拉取过"。
   - **可见的降级**：`active_limits()` 返回 `capability_missing`（`no_active_model` / `not_fetched`），
     写进运行清单并在运行记录顶部提示"按固定额度运行"。
   - **选模即刷新**：`POST /api/providers/{id}/active` 成功后自动 `fetch_models` 一次落库，
     返回 `capability_refreshed`；失败只 toast 提示，不阻断选模。
