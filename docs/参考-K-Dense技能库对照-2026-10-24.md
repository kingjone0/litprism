# 参考 K-Dense 技能库：可借鉴项与冲突评估

2026-10-24。分析对象：[K-Dense-AI/scientific-agent-skills](https://github.com/K-Dense-AI/scientific-agent-skills)
（v2.72.0，177 个科研技能，MIT）。

**本文只做评估，不改代码。** 每一项都写明与现有实现的冲突，以及"能不能顺手做"。

---

## 结论摘要

| 编号 | 借鉴项 | 冲突等级 | 结论 |
|---|---|---|---|
| A1 | 质量面板**字段不消失**（缺席也要显式） | 低 | **采纳**，可立即做 |
| A2 | `not_applicable` 第三态 | **高**（动召回分母 + 需人工标注） | 暂缓，需先定口径 |
| B | 数值对齐（陈述里的数字必须在原文里） | 中 | **采纳**，但只做确定性检查 |
| C | 撤稿/更正状态 | 中高（schema + 外部调用 + 状态语义） | 采纳，排最后 |
| D1 | 技能结构守卫 | 低（但当前无技能实例） | 缓做 |
| D2 | `last-reviewed` 元数据 | 低 | 缓做 |
| D3 | 版本递增强制 | 中（无版本历史） | 只做格式校验 |

## 一、为什么不能"搬技能"

| | K-Dense | LitPrism |
|---|---|---|
| 技能形态 | `SKILL.md` 知识文档 + 可选 `scripts/` | `manifest` + `prompt.md`，声明式 |
| 可执行代码 | 允许（`allowed-tools: Read Write Bash`） | **明确禁止**，只调内核能力 |
| 信任模型 | 安全扫描 + 用户安装前自审 | 能力白名单（`capabilities`） |
| 分发 | `npx skills add` / `gh skill install` | 内置/本地目录 |

依据：`skills/manifest.py:SkillManifest`（trigger/inputs/context/capabilities/output/model）
与 `skills/runner.py`。**结论：可借判据，不可搬技能。**

## 二、A1 质量面板字段不消失（采纳）

### 他们的做法

`scholar-evaluation` 对每个准则要求三态之一：`rated` / `missing` / `not_applicable`，并明确：

> A rated zero requires inspected evidence demonstrating lack of support;
> unavailable evidence is `missing`. **Do not encode missing or not-applicable as zero.**

### 我们的现状（问题）

`quality.aggregate` 里字段槽**只由陈述或补录创建**：

```python
for item in items.values():
    f = slot(item.get('field'))       # 只有出现陈述才建槽
for claim in manual or []:
    slot(claim.get('field'))['manual'] += 1
```

后果：某字段机器一条都没提出、也没人补录时，**这一行从质量面板直接消失**。
用户无法区分三种情况：

1. 机器漏提了这个维度；
2. 这篇论文本来就没有这个维度（纯理论论文没有"实验设计"）；
3. 人还没审到。

第 1 种正是我们最该暴露的漏提信号，现在不可见。

### 冲突

| 冲突 | 说明 |
|---|---|
| 与"分字段"设计 | 无冲突，反而是补全。`summarize` 已按 `total` 降序，空字段排最后 |
| 与 `has_data` | 无冲突。仍按 `reviewed/manual` 判定，空字段不会把 `has_data` 变 true |
| 与现有测试 | `test_quality.py` 多用 `next(f for f in fields if ...)`，新增空字段不影响；`test_fields_sorted_by_total` 仍成立 |
| 前端 | 需确认表格能渲染 0 条行（当前无条件渲染，应该可以），但"覆盖 0%"会与"没这个维度"混淆 → 文案要写"未提取" |

### 最小改动

1. `aggregate()` 结束前，为 `FIELDS` 里**所有**字段建槽（已存在的保持原值）；
2. `summarize()` 给 `total == 0` 的行加 `status: 'not_extracted'`；
3. 前端该行"覆盖"列显示 `未提取` 而不是 `0%`（`0/0` 本来就是 `None`，已显示 n/a，但要换成更准的措辞）。

### 验收

- 一篇只提到 3 个字段的论文，质量面板出现 **6 行**，其余 3 行标"未提取"；
- `has_data` 与合计不受影响；
- 空字段的 `coverage` 仍为 `None`（不是 0%）。

## 三、A2 `not_applicable` 第三态（暂缓）

### 为什么诱人

能区分"机器漏了"与"这篇本来没有"。纯理论论文的"实验设计"标成不适用，
比标成"未提取"更准确，也能把该字段**排除出召回分母**。

### 为什么不能顺手做（冲突）

| 冲突 | 说明 |
|---|---|
| **动召回分母** | 标了 `not_applicable` 的字段若仍计入分母，召回被稀释；若剔除，口径变了 —— 这是**指标定义变更**，必须单独决策并写进文档 |
| 谁来判定 | 机器判断"这篇没有实验设计"不可靠（可能只是没读到）。只能人工标 |
| 存储 | 需按**分析版本**存（像 `manual_claims` 绑 `analysis_hash`），不能按论文存 —— 换一版分析，适用性可能变 |
| 新增写操作 | 面板要加"标为不适用"的入口 + 撤销 + 审计，工作量接近 N05 |
| 与 N05 的关系 | 补录的召回口径会同时受两套规则影响，容易互相解释不清 |

**结论**：先做 A1 拿到"缺席可见"，积累一段真实数据后再看有多少字段真的"不适用"。
如果绝大多数缺席都是"漏提"，那 A2 就不值得做。

## 四、B 数值对齐（采纳，但只做确定性检查）

### 他们的做法

`peer-review` 对每条 claim 要求记录：

> Direction, magnitude, population, outcome, timepoint, and uncertainty alignment

即不只看"有没有引用"，还要看**方向/量级/人群/结局/时间点/不确定性是否对得上**。

### 我们的现状（比预想的更接近）

`gates.py` **已有** `numeric_claims()` 与 `numeric_parse` 闸门，但只检查：

> 含数字的陈述必须能抽出数字，否则说明表述模糊（`gates.py:141-148`）

**它检查的是"陈述里有没有数字"，不是"这个数字在原文里有没有"。**
所以"28.4 BLEU"写错成"24.8 BLEU"照样过闸门 —— 这正是状态页欠账 #3
「机械数值原型未接入生产」的实际形态。

### 冲突

| 冲突 | 说明 |
|---|---|
| **`evaluate()` 拿不到原文** | 签名只有 `data`（字段文本）与 `issues`，没有引用片段。要加 `sources: dict[tag, text]` 参数 |
| 与 LLM 复核的分工 | 6 个维度里只有"量级"可确定性判定；方向/人群/时间点要模型判断，会**增加复核成本与超时风险**（整篇复核曾超时） |
| 与引用标记格式耦合 | 陈述里的 `[P1 p.3]` 要先解析出 tag，再查对应 chunk 文本 |

### 最小改动（只做量级）

1. `evaluate(..., sources: dict[str, str] | None = None)`，调用方传入 `{tag: chunk_text}`；
2. 新增闸门 `numeric_align`：对 `numeric_claims()` 的每条，抽出数字（含单位），
   若该陈述引用的所有 chunk 文本里都找不到这个数字 → `flag`；
3. 无 `sources` 时该闸门 `skip`，不误报（保持向后兼容）。

### 验收

- 把一条陈述的 "28.4" 改成 "24.8"，闸门必须 `flag` 并指出是哪条；
- 原文用 "28.4 BLEU"、陈述写 "28.4" → 通过（不因单位缺失误报）；
- 不传 `sources` 时闸门为 `skip`，现有 900+ 测试不受影响。

### 不做的部分

方向/人群/时间点/不确定性**不进结构化字段**，只作为提示词改进项
（`prompts.py` 里加一句"数值、人群、时间点必须与引用片段一致"）。
理由：模型判定不可复现，且与"分字段人工审核"的现有流程不匹配。

## 五、C 撤稿 / 更正状态（采纳，排最后）

### 他们的做法

`literature-review` 的 pitfall 清单：

> Treating DOI existence as support — a registered DOI can still identify the wrong work;
> check identity, claim support, corrections, and retractions.

### 我们的现状

`verify.py` 已把"题录核验"与"内容可信"分开（`verified` / `manual_confirmed` /
`likely` / `not_found` / `unchecked`），比"DOI 存在即通过"严格。但**没有撤稿/更正检查**。

### 冲突

| 冲突 | 说明 |
|---|---|
| 状态语义 | 撤稿**不能**简单降级 `verify_level` —— 撤稿不等于"题录不存在"。需要独立字段 `retraction_status`（unknown / clear / corrected / retracted） |
| 过期问题 | 检查结果必须带**检查时间**，否则无法判断是否该重查 |
| 外部调用 | 新增 Crossref `update-to` 查询，要进来源白名单与失败降级路径 |
| 与离线降级 | 查询失败必须是 `unknown`，**不得**当成 `clear` |

### 最小改动

1. `papers` 加 `retraction_status`、`retraction_checked_at`（schema v14）；
2. 核验时顺带查 Crossref `update-to` 关系，失败写 `unknown`；
3. 引用/导出前若 `retracted`，必须显式提示并禁止进入可信知识库。

**排最后**：要动 schema + 外部调用 + 状态语义三处，收益（少见但严重）低于 A1/B。

## 六、D 工程实践（低成本，缓做）

| 项 | 他们的做法 | 我们的现状 | 结论 |
|---|---|---|---|
| D1 结构守卫 | `tests/_meta` 检查 frontmatter、文档长度、本地链接、脚本语法、硬编码路径 | `skills/validate.py` 有 Issue 体系，但**当前仓库 0 个技能实例**（无 `skill.yaml`） | 缓做：没有对象可守 |
| D2 `last-reviewed` | 每个 `SKILL.md` 带 `metadata.last-reviewed` | manifest 有 `version`，无最后核对日期 | 缓做：文档已有"更新：日期"，重复度高 |
| D3 版本递增强制 | 更新技能必须 bump `metadata.version` | `version` 默认 `1.0.0`，不校验格式也不比对历史 | 只做**格式校验**（semver 非空），递增需版本历史表，成本不划算 |

## 七、明确不采纳

| 项 | 理由 |
|---|---|
| 177 个领域技能本体 | 定位不同：他们是通用科研工具箱，我们是单篇深度解读 + 质量闭环 |
| `allowed-tools: Read Write Bash` | 与"技能不得执行任意代码"的既有约束直接冲突，不开口子 |
| Agent Plugins / npx 分发 | 我们的技能是内核能力组合，不是可独立分发的知识包 |
| PRISMA / records-reports-studies | 系统综述场景，我们不做系统综述 |
| 安全扫描（`scan_skills.py`） | 我们不执行技能代码，风险面小；若未来开放脚本再引入 |
| 复合评分 | 他们自己也写"overall score never overrides criterion evidence"；我们已坚持分字段不合并 |

---

## 八、建议顺序

```
A1 字段不消失（低冲突，先做）
  → B 数值对齐（中冲突，确定性可测）
  → A2 视数据再定（要改召回口径，单独决策）
  → C 撤稿状态（动 schema + 外部调用，排最后）
```

**不做**：D1/D2/D3（当前无技能实例，收益为零）。
