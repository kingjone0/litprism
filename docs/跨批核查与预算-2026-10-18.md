# 跨批核查的连坐问题与预算参数

2026-10-18（第三轮）。接上一轮 [相邻证据补足](相邻证据补足-2026-10-18.md)。

## 现象：一篇 5 页论文的 19 条陈述全部变待审

用真实模型跑 fastText v3（SHA256 `6cbcf62…`，22 个片段 → 19 条陈述），结果 `19/19 needs_review`，
其中 17 条的说明是「存在全文差异候选或跨批核查未覆盖」。

## 定位

`reconcile()` 的跨批比较在任意一次 `OutputLimitError` 时执行：

```python
skipped.extend(u['id'] for u in units)   # 把所有陈述都标成未覆盖
break
```

一次失败 → 全篇作废。而 `run_review` 在覆盖不完整时把整篇 `passed` 置 false。
于是「1 次网络/额度抖动」升级成「19 条全部不可用」。

**顺便纠正一个我上一轮说错的判断**：我曾说「19 条 → 190 对，40 次上限必然覆盖不全」。
用 stub（返回空差异、零成本）跑真实的 `reconcile` 得到：

```
tiles = 7    cross calls = 27    complete = True    skipped = 0
```

27 对 < 40 上限，**这篇论文的预算本来就够**。O(n²) 只在长论文成立
（那篇 75 页约 34 tile → 595 对，40 上限确实会不够）。

## 修复

1. **单次失败只作废它自己那一对**，不再整篇连坐；
2. 连续失败 `MAX_CROSS_FAILURES = 3` 次才放弃剩余比较（既限制炸钱，又不滥用连坐）；
3. `coverage` 增加 `partial` 字段：区分「部分未覆盖」与「彻底放弃」；
4. 两个**默认值不变**的显式开关（推理模型的思考 token 也计入输出额度，实测会撞顶）：
   - `LITPRISM_REVIEW_MAX_TOKENS`（默认 4096）
   - `LITPRISM_REVIEW_READ_TIMEOUT`（默认 60 秒）

## 实测：修复后同一篇论文

| | 修复前 | 修复后 |
|---|---|---|
| 跨批比较 | 第 2 对就中止，全部 skip | **27/27 对完成**，tiles=7，覆盖 `complete=true` |
| 差异发现 | —（未跑完） | **0 条** |
| 陈述结果 | 19 条全部待审 | 17 条支持 + 2 条待审 |
| 成本 | 20 次调用 / 42.8k token | 27 次调用 / 88.3k token（completion 占 70k） |

那 2 条待审是自身原因，不是被连坐：
- 1 条同时关联 5 个来源（`P21,P22,P3,P7,P9`），要求拆分陈述；
- 1 条模型明确表示该片段不足以支持（sentiment analysis 相关限定缺失）。

**成本结论**：跨批层才是花钱的地方 —— 27 次调用里 completion 高达 70k，
即平均每次约 2600 输出 token，几乎全是推理模型的思考。想降本，应该动这一层而不是复核层。

## 边界（别当成已解决）

- 只验证了**一篇 5 页论文**。长论文的 tile 数会到几十量级，`MAX_CROSS_CALLS=40` 依然是硬约束，
  届时仍需「同字段/同指标分桶」之类的策略改造，而不是调大上限。
- 27 次调用耗时 424 秒（单次 5~20 秒），一篇 5 页论文的跨批阶段就要 7 分钟；长论文需异步/可续跑。
- `partial` 目前只用于报告，界面还没有据此分级展示。
- 上面的「17 条支持」来自**复核层的既有结果 + 本轮跨批层实测**两段拼合，
  不是一次端到端运行的数字（端到端会因网络抖动重新引入未覆盖）。

## 第四轮：长论文的比较范围（为什么单靠调预算行不通）

上一轮把「连坐」修掉了，但长论文的规模问题还在。本轮改成**按字段分桶**比较：

- 「同对象/同指标/同条件下的互斥断言」基本只出现在同一字段内 —— 结论不会去和实验设置打架；
- 桶内仍做完整两两比较，但**跨批优先、距离近的优先**（分歧多出现在分批提取的接缝上）；
- 桶间不比较，`coverage` 如实列出 `fields_done` / `fields_pending`，不把"没比过"说成"通过"；
- 预算可用 `LITPRISM_CROSS_MAX_CALLS` 显式放宽（默认仍 40）。

### 测量（零成本，stub 模型只计数）

| 论文 | 陈述 | tile | 比较次数 | 覆盖 |
|---|---|---|---|---|
| fastText v3（5 页，真实） | 19 | 9 | **11**（原 27） | 完整，5/5 字段 |
| 75 页模拟 | 240 | 82 | **40（撞上限）** | 1/6 字段 |
| 75 页模拟（预算放到 400） | 240 | 82 | **400（仍撞上限）** | 4/6 字段 |

### 结论：长论文的瓶颈不是预算，是策略

240 条陈述 → 82 个 tile，即使只做桶内两两也要几千对。把预算提到 400 次**仍然核不完**，
而实测每次调用约 2600 completion token（推理模型），400 次≈100 万 token。
**继续调大预算既贵又慢，不能解决长论文。**

真正可行的方向只有三条，且都需要产品层面的取舍：

1. **选择性核对**：只对"有风险"的陈述做语义比较 —— 含数值/单位（已有机械 `value_index`）、
   含 all/only/always 等限定词、跨批共享同一 subject+metric 的。其余标"未核对"而非"通过"。
2. **摘要级核对**：每个字段先合成 3~7 条规范断言，再比断言，而不是比每条陈述。代价是精度下降。
3. **界面承担不确定性**：把「未核对」做成一等状态交给用户 —— 也就是下一步要做的证据队列。

在此之前，长论文的正确行为是：**机械层全量跑（引用、逐字、页码、数值索引）+ 语义层只跑能跑完的部分，
并把没跑的部分明确标出来**，而不是宣称整体通过或整体作废。

`pairs_attempted` 只统计「真正开始比较的字段」里计划的对数，撞预算后不会再为后续字段计算；
要看总规模请以 `tiles` 为准。
