# 全文送检：从底层重算核对机制

> 文档状态（2026-10-18 对照）：阶段观察和重构讨论。页数/token/批次取决于具体 PDF、解析与窗口配置，不能推广成所有版本的固定值；“一次送入全文”也不保证只有一次 API 调用或语义一致。 最新实现、未完成项及验证口径见 [当前状态](../当前实现与验收状态.md)，分类入口见 [文档导航](../README.md)。

2026-10-18。回答"要不要保留把全文送进 API"，并据此重排机制。
所有数字均为当前代码实测（零成本 stub 或真实语料）。

---

## 一、先纠正一个前提：多数论文本来就没分批

| 论文 | 页 | 全文 token | 占 32k 窗口 | 实际批次 |
|---|---|---|---|---|
| Attention Is All You Need | 10 | 8,459 | 26% | **1** |
| BERT | 12 | 12,362 | 39% | **1** |
| GPT-3（Language Models are Few-Shot Learners） | 62 | 60,553 | 189% | 3 |

**10–12 页的论文全文只有 8–12k token，早就一次读完了。**
"分批"只发生在长论文上。所以问题不是"要不要全文送检"—— 短论文一直是全文送检。

真正的问题是：**长论文要不要把窗口开大，让它们也变成一次读完。**

窗口实测：

| 窗口 | GPT-3 批次 |
|---|---|
| 32,000 | 3 |
| 64,000 | 2 |
| **128,000** | **1** |

62 页论文在 128k 窗口下只需 1 次调用。**这不是理论，是实测。**

---

## 二、但全文送检本身不解决 O(n²) —— 因为代码不看批次

这是最关键的一点。

`reconcile()` 构建两两比较时，`same_batch` **只用于排序优先级，不用于过滤**：

```python
pairs = [(i, j) for i in range(len(tiles)) for j in range(i, len(tiles))]
pairs.sort(key=lambda ij: (same_batch(*ij), ij[1]-ij[0], ij[0]))
#                              ↑ 只影响顺序，不影响是否比较
```

后果：**即使整篇论文来自同一次模型调用，差异层仍会把所有 tile 两两比一遍。**

而差异层宣称的目标是"避免**分批提取**前后矛盾"。同一次调用产出的陈述，
在"分批"这个意义上不可能互相矛盾 —— 却仍被全量比较。

所以现状是：全文送检省下的批次，**在差异层完全没有兑现**。

---

## 三、量化：批次感知能省多少

240 条陈述 → 84 个 tile（每 tile 3 条）→ 全量两两 = 3,570 对。

| 情形 | 需要比较的对数 | 相对全量 |
|---|---|---|
| 全量（现状） | 3,570 | 100% |
| 3 批，只比跨批 | 2,352 | 66% |
| **1 批（128k 窗口）** | **0** | **0%** |

结论很清楚：

- **单批论文 → 差异层直接消失（0 次调用）**；
- 多批论文 → 只省 1/3，仍然远超 40 次预算。

所以"只做批次感知"对长论文不够，但对**绝大多数论文**是决定性的 ——
它们本来就该是单批。

---

## 四、复核层还有第二道墙，和批次无关

复核层是**一条陈述一次调用**（`if len(current) >= 1` 硬编码），上限 48 次：

| 陈述数 | 调用 | 机器支持 | 未核 |
|---|---|---|---|
| 48 | 48 | 48/48 | 0 |
| 60 | 48 | 48/60 | 12 |
| 120 | 48 | 48/120 | 72 |
| 240 | 48 | 48/240 | **192** |

240 条有 80% 根本没核。而单条复核的输出只有 `{id, verdict, reason, evidence}`，
一次判 8 条约 480 输出 token —— **批量复核完全放得下**，
当初"一条一次"是为了避免输出预算耗尽（旧协议要模型抄引文 + 抽 facts），
协议简化后这个约束已经过时。

---

## 五、重构方案：四层

### 第 0 层 · 体量判定（新增）

```
测量全文 token
├─ ≤ 60% 窗口 → 全文单次读取（单批）
└─ > 60%      → 按章节切分（引言/方法/实验/结论），而不是按固定块数
```

按章节切的理由：章节与字段天然对齐（方法对应 methodology、实验对应 experiment_design），
切在章节边界不会把表格/段落劈成两半 —— 这正是当前"截断导致误判不符"的来源。

**配置缺口**：`window_tokens` 目前是全局值，与模型无关。
换 128k 模型不会自动放大窗口。应改为按提供商配置。

### 第 1 层 · 提取（按字段分调用，而非按文本位置）

整篇论文放进上下文，**一次只提一个字段**：

```
6 个字段 → 6 次调用，每次：全文 + 该字段的提取指令
输出：40 条陈述 × 60 token ≈ 2,400 token（放得下）
```

收益：
- 同一字段的陈述来自**同一次调用** → 该字段内部不存在"跨批矛盾"
- 模型始终看得到全文 → 引用归属、跨章节指代更准
- 输出可预期，不会因为"整篇一次提完"而爆输出

### 第 2 层 · 复核（批量，8 条一次）

协议不变，只改打包粒度：

| | 现状 | 改后 |
|---|---|---|
| 每次判几条 | 1 | 8 |
| 240 条需调用 | 240（实际 48） | 30 |
| 覆盖 | 20% | **100%** |

### 第 3 层 · 差异（机械优先 + 批次感知 + 选择性）

按成本从低到高：

1. **机械数值层**（0 调用）：子句签名比对，覆盖所有含数值陈述（实测占 56%）
2. **跨批语义层**：只比**不同批次**的陈述；单批论文 = 0 次
3. **选择性语义层**：只比"同签名 / 含全称限定词 / 跨批共享指标"的陈述对

## 六、效果预估（基于实测数据）

| 论文类型 | 现状 | 重构后 |
|---|---|---|
| 10–12 页（单批） | 复核 48/48 + 差异 27 次 | 复核 6 次 + 差异 **0** 次 + 机械层 |
| 62 页（128k 窗口） | 复核 48/240 + 差异 40 次（0/6 字段） | 复核 30 次 + 差异 **0** 次 + 机械层 |
| 62 页（32k 窗口） | 同上 | 复核 30 次 + 差异仅跨批 + 机械层 |

关键变化不是"更便宜"，而是**覆盖率从 20% 变成接近 100%**。

---

## 七、风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| 长上下文召回衰减 | 60k token 的中间部分模型可能漏读 | 分字段提问（每字段只关注一类信息）比"一次提全部"更抗衰减；可抽样对照单批 vs 分批的提取质量 |
| 单次调用失败即全丢 | 单批论文一次调用失败，整篇无结果 | 按字段分调用天然提供 6 个独立单元，失败只丢一个字段 |
| 成本上升 | 6 次调用 × 60k 输入 = 360k 输入 token | 输入 token 单价约为输出的 1/4；且换来 5 倍覆盖率 |
| 窗口配置与模型脱节 | 换模型不自动改窗口 | 需把 window_tokens 挪到提供商配置 |
| 章节切分依赖版面解析 | 部分 PDF 章节识别不准 | 识别失败时退回固定块切分，并在 coverage 里标注 |

## 八、待确认

1. **是否把"全文单次读取"作为默认策略**（论文 ≤ 60% 窗口时）？
2. **提取改为按字段分调用**（6 次，每次全文）—— 认可这个方向？
3. **复核改批量（8 条/次）** —— 需要先做一次真实模型实测确认输出不截断。
4. **差异层加批次过滤** —— 这是纯逻辑修复，无风险，建议先做。
5. **window_tokens 挪到提供商配置** —— 需要 schema v4。

建议顺序：④（无风险，立刻减少无谓调用）→ ③（批量复核，解决 80% 未核）→ ②（字段分调用）→ ①（体量判定）→ ⑤（配置）。
