# 文献棱镜 LitPrism · Skill 框架设计

> 文档状态（2026-10-18 对照）：声明式 Skill 框架已接通输入、范围、证据守卫及产出流程；不是任意脚本执行或无约束工具循环。未对术语/QA/Skill 宣称与六字段解读同等的逐条语义验收。 最新实现、未完成项及验证口径见 [当前状态](../当前实现与验收状态.md)，分类入口见 [文档导航](../README.md)。

> 一期交付**框架**，**不内置任何 Skill**。
> 日期：2026-10-16 · 状态：待确认

---

## 一、为什么"先建框架、内容留白"

这个顺序是有意选的，理由有三：

1. **框架是架构决策，内容不是。** 扩展点的形状一旦定错，后面每加一个 Skill 都要绕；
   而定对了，加内容只是写两个文件。
2. **空容器能真实验证"扩展点够不够用"。** 如果框架只在自己人写的 Skill 上验证过，
   很容易把"恰好够用"当成"足够通用"。留白反而逼着我们把接口设计干净。
3. **验证不依赖内置 Skill。** 用测试夹具（临时目录构造的 Skill）覆盖框架行为，
   而不是靠"顺手写一个 Skill 来测"—— 后者会让测试和业务耦合。

## 二、目录与文件

```
<数据目录>/skills/                 ← 用户添加的 Skill（包内不预置）
  <skill-id>/
    skill.yaml                     ← 清单（必需）
    prompt.md                      ← 提示词模板（必需）
    README.md                      ← 可选，说明用途
```

- Skill 目录**只读加载**，框架不执行目录内任何脚本
- 加载失败时给出可读错误，**不影响应用启动**
- 包内不预置 `skills/` 内容，设置页显示空状态引导

## 三、清单规范 `skill.yaml`

```yaml
# ---- 元数据 ----
schema_version: 1                  # 框架版本，用于兼容性检查；不匹配则拒绝加载
id: literature-review              # 唯一标识：小写字母、数字、连字符
name: 文献综述生成                  # 界面显示名
version: 1.0.0
description: 基于知识库中的已核验文献生成带引用的综述草稿
author: ""                         # 可选

# ---- 触发 ----
trigger:
  prefix: "综述"                    # 输入框快捷前缀（可选）
  keywords: ["综述", "literature review", "研究现状"]   # 命令面板检索关键词

# ---- 输入契约 ----
inputs:
  - key: scope
    label: 文献范围
    type: collection               # collection | papers | topic | text | number
    required: true
  - key: focus
    label: 侧重方向
    type: text
    required: false
    placeholder: 例如：注意力机制的演进

# ---- 声明式上下文预取（不是工具调用循环）----
context:
  - capability: search_passages
    query: "{{focus}}"
    top_k: 30
  - capability: get_analysis
    scope: "{{scope}}"

# ---- 能力白名单（超出即校验失败）----
capabilities:
  - search_passages
  - search_papers
  - get_analysis
  - list_collections

# ---- 输出 ----
output:
  type: deliverable                # deliverable | answer | analysis
  deliverable_type: review         # 仅 type=deliverable 时有效
  citation_required: true          # 强制走引用回溯校验

# ---- 模型参数覆盖（可选）----
model:
  temperature: 0.2
  max_tokens: 8192
```

### 校验规则

| 规则 | 失败处理 |
|---|---|
| `schema_version` 必须等于框架支持的版本 | 拒绝加载，提示版本不兼容 |
| `id` 必须匹配 `^[a-z0-9][a-z0-9-]{1,48}$` 且与目录名一致 | 拒绝加载 |
| `capabilities` 中每一项必须在**固定能力表**内 | 拒绝加载，列出非法项 |
| `prompt.md` 必须存在且非空 | 拒绝加载 |
| `inputs` 中 `required: true` 的项必须在 `prompt.md` 中被引用 | 警告（不阻止） |
| `prompt.md` 中出现的 `{{var}}` 必须在 `inputs` 中声明 | 拒绝加载，列出未声明变量 |
| `output.citation_required: true` 时，`prompt.md` 需含引用标记说明 | 警告 |

**设计取向：能拒绝的早拒绝，不确定的只警告。** 校验失败不静默降级 ——
静默降级会让用户以为 Skill 生效了，实际行为不同，这比直接报错更糟。

## 四、固定能力表

Skill 只能调用下列能力，**不可扩展**：

| capability | 说明 | 返回 |
|---|---|---|
| `search_passages` | 检索原文片段 | 片段列表（含 paper_id / page / section / text） |
| `search_papers` | 检索题录 | 论文列表（含核验状态） |
| `get_analysis` | 取结构化解读 | 研究问题/方法/实验/结论/创新点/局限 |
| `list_collections` | 分组树 | 分组与所含论文 |
| `get_graph` | 知识图谱数据 | 节点 + 边 |
| `verify_paper` | 核验论文真实性 | 四态判定 + 候选匹配 + 证据 |
| `compare_papers` | 多篇对比 | 六维度矩阵 |

这些能力**全部来自内核**，Skill 通过声明调用，不能自带实现。

## 五、执行契约

```
① 加载并校验 manifest
② 按 context 声明预取上下文（只调用白名单内的能力）
③ 渲染 prompt.md（替换 {{var}}）
④ 组装最终提示词：
     全局学术规范与防幻觉约束（框架强制前置，不可移除）
   + Skill 提示词
   + 预取上下文
   + 用户输入
⑤ 调用模型
⑥ 后处理：
     citation_required=true → 强制走引用回溯校验（与问答同一套实现）
     校验不通过 → 标记「引用校验未通过」并显式提示，不静默放行
⑦ 落库或返回
```

### 关于"声明式预取"而非"工具调用循环"

一期采用**声明式上下文预取**：Skill 在清单里写清需要哪些检索，
框架在调用模型前一次性取好并注入提示词。

对比工具调用循环（让模型自己决定调哪个工具、调几次）：

| 维度 | 声明式预取 | 工具调用循环 |
|---|---|---|
| 可控性 | 高 —— 检索范围可预测 | 低 —— 依赖模型判断 |
| 防幻觉 | 容易 —— 上下文即全部证据，可精确校验引用 | 难 —— 证据分散在多轮中 |
| 成本 | 可预估 | 不可预估（可能多轮） |
| 实现复杂度 | 低 | 高（循环、超时、终止条件） |
| 灵活度 | 低 | 高 |

一期选声明式，因为**防幻觉优先于灵活度**。二期若确有需要，再在框架里增加工具调用模式。

## 六、安全边界

### 6.1 一期只支持声明式 Skill，不支持自定义代码

**这是硬性边界。** 允许 Skill 携带可执行代码 = 开放任意代码执行入口，
用户从别处拿来的 Skill 就能在你机器上跑任意逻辑。要支持就必须先有沙箱方案，
而那是一整套独立工程，不该混在 Skill 框架里顺手做。

一期的 Skill 能做的是：**声明提示词 + 声明输入 + 声明要哪些上下文 + 声明输出形态**。
仅此而已。对绝大多数"换个问法、换个输出格式"的需求，这已经够了。

### 6.2 防幻觉约束不可绕过

- 全局学术规范与防幻觉约束由框架**强制前置**，Skill 作者无法移除或覆盖
- `citation_required: true` 时，引用校验由**框架**执行，不依赖 Skill 作者自觉
- 能力白名单外的调用一律拒绝加载
- Skill 的输出若进入知识库，同样受导入守卫约束（未核验不入库）

**这一条是刻意设计的**：用户自行添加的 Skill 是系统里最不可信的输入源，
如果它能绕过防幻觉约束，前面三层防线就白建了。

### 6.3 其他

- Skill 目录只读加载，不自动执行任何脚本
- 加载失败不影响应用启动，错误在设置页可见
- Skill 生成的交付物标注来源 Skill 与版本，便于追溯

## 七、界面

设置页新增 **「Skill」分区**（替代原「提示词」分区）：

| 区域 | 内容 |
|---|---|
| 已加载 Skill 列表 | 名称、id、版本、作者、状态（正常 / 校验失败）。一期为空 |
| 空状态引导 | "尚未添加 Skill。Skill 是声明式的提示词扩展，可在下方目录放置。"+ 打开目录按钮 |
| 导入 / 新建 | 从文件导入 Skill 包（zip / 目录）；按模板新建（生成 `skill.yaml` + `prompt.md` 骨架） |
| 校验结果 | 每个 Skill 的校验明细（失败项逐条列出，含修复建议） |
| 内核提示词 | 折叠区：查看与微调内核内置的提示词（结构化解读、术语、问答、对比、查询扩展） |

**注意区分两件事**：

- **内核提示词** —— 结构化解读、术语解释、问答、对比、查询扩展。
  这些是内核能力，**不是 Skill**，硬编码在 `prompts.py`，只提供查看与微调。
- **Skill** —— 用户自行添加的扩展，走框架加载。一期为空。

命令面板（`Ctrl+P`）会列出可用 Skill 与内核能力；
一期只有内核能力，Skill 区域显示空状态。

## 八、验证方式（零内置 Skill）

单元测试用**临时目录构造夹具 Skill**，覆盖以下场景：

| 场景 | 断言 |
|---|---|
| 正常加载 | 清单解析正确，能力白名单生效 |
| `schema_version` 不匹配 | 拒绝加载，错误信息含版本号 |
| `id` 与目录名不一致 | 拒绝加载 |
| `capabilities` 含非法项 | 拒绝加载，列出非法项 |
| `prompt.md` 缺失或为空 | 拒绝加载 |
| `prompt.md` 含未声明变量 | 拒绝加载，列出未声明变量 |
| 正常执行 | 预取上下文正确注入，提示词含全局约束 |
| `citation_required: true` 且模型输出无引用 | 引用校验拦截，标记未通过 |
| 损坏的 yaml | 不抛异常，返回可读错误，应用仍可启动 |

这样框架的正确性**不依赖任何内置 Skill**，与"不添加 Skill"的要求一致。

## 九、二期可扩展方向

| 方向 | 前置条件 |
|---|---|
| 代码型 Skill | 需先设计沙箱（进程隔离 / 权限限制 / 资源上限） |
| 工具调用循环模式 | 需解决证据分散下的引用校验问题 |
| 输入表单自动生成 | 从 `inputs` schema 生成 UI 控件（一期先做基础类型） |
| Skill 依赖与版本管理 | 需要包管理与冲突解决策略 |
| Skill 分享与校验 | 需要签名机制，否则无法判断来源可信度 |
