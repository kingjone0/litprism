# 效果评判：让阅读本身成为标注

> 文档状态（2026-10-18 对照）：评测方案。已有 eval_extraction.py 聚合现存人工审核，但 E-1 漏提补录、质量面板及完整阅读即标注/A-B 尚未落地；库内审核数和模型容量数字仅为当时观察，不能当作当前账户/数据状态。 最新实现、未完成项及验证口径见 [当前状态](../当前实现与验收状态.md)，分类入口见 [文档导航](../README.md)。

2026-10-18。承接 [全文送检与机制重构](全文送检与机制重构-2026-10-18.md)。
用户指出：1M 上下文下长文放得下，**约束已从"容量"转移到"效果"**，
而效果评判需要人工参与 —— 且这种参与应当同时丰富知识库。

---

## 一、1M 上下文改变了什么，没改变什么

| | 改变 | 说明 |
|---|---|---|
| 输入容量 | ✅ 约束消失 | 62 页论文 60k token，1M 窗口下只占 6% |
| 分批必要性 | ✅ 大幅下降 | 除超长专著，基本不再需要按位置切块 |
| **输出容量** | ❌ **没变** | 一次调用提不出 240 条陈述（输出上限 4–8k token） |
| **注意力质量** | ❌ **反而更关键** | 60k token 的中段召回会衰减，但**没人知道衰减多少** |

结论：
- **"按字段分调用"仍然必要**，但理由变了 —— 不是装不下，而是**输出装不下**；
- 新的核心风险是**长上下文里漏读/误读**，这类问题只能靠人看出来。

**所以真正的缺口不是机制，是评测。** 现在的机制可以在 1M 窗口上跑，
但没有任何证据说明它跑得好不好 —— 库里 `semantic_reviews` 记录数为 **0**。

---

## 二、效果要评三件事，现在只能测一件

| 维度 | 定义 | 现状 |
|---|---|---|
| **精度** | 机器说的对不对 | ✅ 可从审核记录算 |
| **召回** | 该说的有没有说 | ❌ **无法测量** |
| **人工成本** | 确认一条要多久 | ⚠️ 可测，未采集 |

已实现（`tools/eval_extraction.py`，合成数据自检通过）：

```
字段           陈述   已审   逐字   修正   拒绝     逐字精度     可用率     复核覆盖
主要结论          3    3    1    1    1      33%     67%     100%
方法            2    1    1    0    0     100%    100%      50%
局限            1    0    0    0    0        —       —       0%
合计            6    4    2    1    1      50%     75%      67%
召回（漏提）：n/a —— 审核界面没有「补一条机器未提及的陈述」入口，无法测量
```

指标全部从**已有数据**推导，不新增采集：
- `confirm` 且 `reviewed_text == 原陈述` → 逐字
- `confirm` 且 `reviewed_text != 原陈述` → 修正（方向对、表述需纠正）
- `reject` → 拒绝
- `revoke` 是回退动作，不计入样本

---

## 三、召回为什么测不了，以及怎么补

精度只需看机器说了什么；召回要看**机器没说什么** —— 必须有人把漏掉的指出来。

现在审核界面只有「确认 / 修正 / 拒绝 / 撤销」四个动作，全部作用于**机器已经提出的陈述**。
所以无论人审多少遍，都产生不了召回信号。

### 补法：一个「补一条」动作

在阅读界面上：

```
选中原文里的一句话 → 「补一条陈述」→ 选字段 → 保存
```

它同时做三件事：
1. **产生召回信号**：人工新增数 / (机器陈述 + 人工新增) = 漏提率
2. **产生正样本**：这句话是真陈述，且能直接绑到原文 —— 天然的 gold label
3. **丰富知识库**：确认后与机器陈述走同一条入库路径

成本几乎为零 —— 用户本来就在读那句话。

---

## 四、阅读即标注：把审核界面做成阅读界面

现在的审核是「逐条点开右栏看原文」，本质是**清单核对**，人是被机器牵着走的。
更好的形态是**以原文为主线**：

```
┌─────────────────────────────┬──────────────────────────┐
│ 论文原文（按章节连续阅读）      │ 本字段的机器陈述（按位置锚定）│
│                             │                          │
│ …句1 …句2【高亮】…句3…        │ ● 陈述A  ✓确认 ✎修正 ✗拒绝 │
│          ↑ 对应陈述A          │ ○ 陈述B  ✓确认 ✎修正 ✗拒绝 │
│ …新增：选中句子 → 补一条…      │                          │
└─────────────────────────────┴──────────────────────────┘
```

关键差别：
- 人按**自己的阅读顺序**走，机器陈述作为旁注出现；
- 读到机器漏掉的，就地补一条；
- 读完后，这个字段既被核对完，知识库也长了一截。

**审核动作即标注动作，阅读时间即标注时间。** 这是唯一可持续的评测方式 ——
否则"评测"会变成一件额外的工作，没人会做。

---

## 五、策略对照：只裁决差异

要回答"全文单次 vs 分批哪个效果好"，不需要把两种结果都全量标注。

```
同一篇论文，跑两种策略 → 两份陈述集
        ↓
按（字段, 归一化文本）对齐
        ↓
三类差异：只在 A / 只在 B / 两边都有但引用不同
        ↓
人只裁决这三类（通常远少于总陈述数）
```

产出：
- **分歧率** —— 两种策略差异有多大
- **各自在分歧项上的正确率** —— 谁更好，且能看出好在哪里（漏提 vs 多提 vs 引错）
- 裁决结果沉淀为 gold 样本，下次可直接回归

这比"跑两遍然后人工全看"便宜一个数量级。

---

## 六、口径纪律（避免自欺）

1. **召回未采集时显示 `n/a`**，不用"确认率"冒充召回；
2. **复核覆盖低时指标不具代表性**，必须同时显示 `已审/总数`；
3. 人工确认表示"接受这份快照"，**不等于内容客观真实**；
4. 分字段报告 —— 总体 80% 可能掩盖"局限"字段 20%；
5. 机器支持、人工确认、原文覆盖是**三种不同状态**，不可合并成一个"通过"。

---

## 七、落地顺序

| 步 | 内容 | 依赖 | 价值 |
|---|---|---|---|
| **E-1** | 「补一条」动作 + 入库 | 无 | **召回从此可测**，这是评测的地基 |
| **E-2** | 指标聚合接入界面（复用 `eval_extraction.py`） | E-1 | 每篇论文一个质量面板 |
| **E-3** | 阅读即标注的界面重排 | E-1 | 降低人工成本，让评测可持续 |
| **E-4** | A/B 策略对照工具 | 需真实模型 | 用数据回答"全文 vs 分批" |
| **E-5** | 注意力衰减探测（长文中段抽样核对） | 1M 模型 | 量化"漏读" |

**建议先做 E-1**：它最便宜，却把"召回不可测"这个根本缺口补上了。
在此之前，任何"效果好不好"的结论都只有一半证据。
