这一版取代 [任务计划分配设计](任务计划分配设计-2026-10-18.md) 里的"切块送"作为主路径；
切块降级为超长文档的兜底。

---

## 一、为什么这个方案更好

| | 切块送（我上一版） | **全文驻留 + 变指令（本版）** |
|---|---|---|
| 上下文碎片化 | 有，跨章节指代会丢 | **无，模型始终看得到全文** |
| Prompt 缓存 | 每次内容不同，几乎不命中 | **原文前缀固定 → 可命中** |
| 注意力控制 | 靠"只给这段"物理隔离 | 靠指令定向 + 物理全文兜底 |
| 需要管的 | 输入切分 + 输出配额 | 完整输入预算、目标范围与输出配额 |
| 跨段一致性 | 靠事后差异层补 | 各次请求共享原文，但仍需核对跨调用差异 |

关键收益是第三条：**模型永远能看到全文，所以"如 3.2 节所述"这类指代不会断**。
我上一版为了控制注意力把上下文切碎，反而制造了新的断裂。

## 二、但有一个前提：消息布局必须反过来

现有代码（`extract.py:80`）：

```python
ctx = instruction + '\n\n' + excerpt_text(excerpts)
#      ↑ 变化的指令在最前面
```

**前缀缓存匹配的是最长公共前缀。指令放最前面 = 每次都从第一个 token 开始不匹配 = 永远不命中。**

必须改成原文在前、指令在后：

```python
messages = [
    {'role': 'system', 'content': SYSTEM},              # 固定
    {'role': 'user',   'content': PAPER_TEXT + '\n\n' + DIRECTIVE},   # 前缀固定，尾部变化
]
```

并且 **PAPER_TEXT 必须字节级稳定** —— 每次从库里取都要按 chunk 序号排序、用固定分隔符拼接。
差一个空格就整段缓存失效。

## 三、计划从"上下文切片"变成"注意力指令"

### 旧计划（切片）
```json
{"task": {"field": "methodology", "sections": ["s3"], "input_tokens": 6800}}
```

### 新计划（指令）
```json
{
  "paper_id": "p_x",
  "context": {"tokens": 60553, "cache_key": "sha256:..."},
  "directives": [
    {
      "id": "d1",
      "focus": "第 4 节（结果）第 1/3 段，约 7k token",
      "quota": 44,
      "expected_claims": [24, 41],
      "fields": ["experiment_design", "key_conclusions"],
      "reason": "结果节 21k token ≈ 94 条，超配额 → 拆 3 段"
    }
  ]
}
```

**分配依据是"预估条数"，不是"字数"**：

```
预估条数 = 章节 token × 4.5
```

### 贪心装箱（实测）

`max(1, ⌈est/quota⌉)` 会让每个小节各占一次调用（摘要 2 条也占一次），浪费。
改成**按预估条数贪心合并到配额上限**：

| 论文 | 全文 token | 指令数 |
|---|---|---|
| Attention（10 页） | 8,459 | **1** |
| BERT（12 页） | 12,362 | **2** |
| GPT-3（62 页） | 60,553 | **9** |

GPT-3 的 9 条：

```
d1-d3  结果（21k token，拆 3 段）
d4-d5  方法（13.5k，拆 2 段）
d6     局限
d7     背景
d8     结论 + 引言
d9     相关工作 + 实验 + 摘要 + 正文
```

**单条指令仍然提取全部六个字段** —— 与现有 `EXTRACT_SYSTEM` 一致，不改协议。
字段的"提薄了"由闸门检测（见第四节），而不是靠拆字段来控制。

这样比"6 字段 × N 段"的笛卡尔积少一个数量级：GPT-3 从 54 次降到 9 次。

## 四、输出配额怎么保证

三道机械闸门，全部零成本：

1. **配额**：每条指令 `quota=44`（4096 预算 × 70% ÷ 64 token/条）
2. **截断检测**：JSON 不完整 → 该指令一分为二（按 focus 的前后半段），重跑
3. **条数校验**：实际 < 期望下限 → 疑似漏读 → 重跑；> 上限 → 疑似编造 → 标待人工

第 2 条是输出容量的真正保障 —— 不靠预估准，靠**截断后自动细分**兜底。

## 五、缓存收益（这是本方案最大的隐性收益）

GPT-3，60k 上下文，9 条提取指令 + 30 条复核 + 10 条差异 ≈ 49 次调用：

| | 无缓存 | 有前缀缓存（按 90% 折扣） |
|---|---|---|
| 首次 | 60k | 60k |
| 后续 48 次 | 48 × 60k = 2,880k | 48 × 6k = 288k |
| **合计** | **2,940k** | **348k** |

**约 8.4 倍差距。** 而且这个收益完全来自"上下文不变"这一条设计 ——
一旦按章节切块送，每次内容不同，缓存全废。

> 折扣因提供商而异：DeepSeek 命中约 1/10 价，OpenAI 约 5 折，Anthropic 需显式
> cache_control 断点（约 1/10）。`llm.py` 已记录 `last_usage`，里面含
> `prompt_cache_hit_tokens` —— 但目前没有暴露成指标，应该接到评测面板里。

## 六、注意力质量：仍然只能检测

全文驻留不会消除 "lost in the middle"。60k 的中段依然会被低估。
指令能缓解（明确点名"第 3 节 3.1–3.2"），但不能保证。

**检测手段不变**：每条指令都有 `expected_claims` 区间，实际条数低于下限就是漏读信号。

新增一个更有针对性的检测：**跨指令重复率**。
如果 d1 和 d2 都声称覆盖方法节，但 d2 提出的陈述有 80% 与 d1 重复，
说明 d2 其实没读到自己的重点段 —— 这也是注意力失效的信号。

## 七、修订后的架构

```
① 装载：论文全文一次性序列化（字节稳定）→ 作为固定前缀
② 计划：按「预估条数 ÷ 配额」生成注意力指令清单（不切上下文）
③ 执行：每条指令一次调用，前缀相同、尾部不同 → 命中缓存
④ 闸门：JSON 完整 / 引用存在 / quote 逐字 / 数值可解析 / 条数区间
⑤ 修复：只重跑未通过的指令，≤2 轮；截断则对半细分
⑥ 兜底：论文 token > 窗口 70% 时，才退回切块模式（并标注）
```

对比我上一版，**唯一但关键的区别是 ③**：不再切上下文，只换指令。

---

## 八、这样能不能达到你要的效果

| 目标 | 结论 |
|---|---|
| 输出容量 | ✅ 配额 + 截断自动细分，双保险 |
| 注意力质量 | ⚠️ 不能保证，靠条数区间 + 重复率检测 |
| 全文常驻、无碎片 | ✅ 这是本方案的核心优势 |
| 成本 | ✅ 缓存命中后约 1/8 |
| 可评测 | ✅ 指令级条数区间、缓存命中率、重复率都可测 |
| 可复现 | ✅ 计划是确定性生成的 JSON，可存档可重放 |

**唯一没解决的还是"注意力到底读全了没有"** —— 这个只能靠人在中段抽样核对，
也就是「阅读即标注」。分配算法把它从"全篇不可知"缩小到"某条指令的某一段可疑"，
但不能替你消除它。

### P-3 完成记录：闸门 + 有界修复

新增 `src/litprism/gates.py`（纯函数、零模型成本）：

| 闸门 | 判断 | 失败动作 |
|---|---|---|
| `json_complete` | 返回是可解析对象 | 重跑 |
| `has_citation` | 每个非空字段带来源 | 标记 |
| `numeric_parse` | 含数字的陈述能抽出数值 | 标记 |
| `section_coverage` | 条数落在期望区间 | **低于下限 → 重跑**；高于上限 → 标记 |
| `citation_issues` | 页码/片段引用问题 | 标记 |

**只有 `section_coverage` 低于下限会触发重跑** —— 它也是注意力质量的唯一可观测代理。

**修复有界**：最多 1 次初始 + 2 次重跑；**修完更差就不采纳**（按"闸门通过数 → 产出条数"打分）。
修完仍不过的如实记未覆盖，绝不伪装成通过。

**截断处理**：`OutputLimitError` 不再让整次解读失败，而是把该单元记为未覆盖并写进
`coverage.uncovered_units`。自动对半细分留到下一版（需要重新规划指令）。

**实测（欠产出桩模型）**：

```
第 1 次调用 → 1 条陈述，期望 26–49 条 → 触发修复
第 2 次调用 → 30 条 → 通过
合计 2 次调用，coverage.complete = True
```

**顺带修**：`results` 为空时 `dict(results[0])` 会 IndexError，改为给全空骨架，
让下游看到"无内容 + 未覆盖"而不是整次失败。

测试：`tests/test_gates.py` 21 项。全量 **710 项通过**。

### P-4 完成记录：用量与缓存命中归集

新增 `src/litprism/usage.py`。三家提供商的 usage 字段名完全不同：

| 提供商 | 输入 | 输出 | 缓存命中 |
|---|---|---|---|
| OpenAI | `prompt_tokens` | `completion_tokens` | `prompt_tokens_details.cached_tokens` |
| DeepSeek | `prompt_tokens` | `completion_tokens` | `prompt_cache_hit_tokens` |
| Anthropic | `input_tokens` | `output_tokens` | `cache_read_input_tokens` |

`normalize_usage()` 统一成 `{input, output, cache_hit, cache_miss, cached_ratio}`，
`UsageTracker` 按任务累计。结果写入 `coverage.usage`，界面显示命中率徽章。

**口径纪律**：提供商没报缓存字段时给 **`None`（"不可知"）而不是 0** ——
0% 会被读成"缓存没生效"，而实际可能是"这家根本不报"。

**修掉一个真 bug**：原实现先推算 `miss = total_in - hit`，再判断"有没有报缓存"，
导致没报缓存的提供商被算成"命中 0%"。已改为**先判断再推算**。

### P-5b 完成记录：跨指令重复检测

条数闸门能抓"提得少"，抓不到"提得多但全是从别处搬来的"。
如果指令 d2 声称只看第 5 节，却把 d3 的陈述又抄了一遍，条数看起来正常，
实际上 d2 根本没读自己的范围。

实现：按句比对（token + 中文 bigram 的包含度），单句相似度 ≥0.8 算重复；
整个单元 ≥80% 重复 → 告警，写入 `coverage.overlaps`，界面显示。

**实测（两条指令返回相同内容）**：

```
指令 2 条 | 调用 4 次 | 命中率 62%
重复告警：d2 的 100% 陈述与 d1 高度重合 —— 可能没有读取自己的范围
闸门：d1 未过 section_coverage（20 条 < 期望 25），d2 通过
```

测试：`tests/test_usage.py` 13 项 + `test_gates.py` 新增 7 项重复检测。
全量 **730 项通过，21 秒**。

## 十、真实模型实测（deepseek/deepseek-v4.1-flash）

提供商：CommandCode 网关（已从 `E:/codex-litprism-data` 迁移到主工作区，密钥 DPAPI 解密正常）。
论文：Attention Is All You Need（8,459 token，42 块）。窗口 128k，输出预算 32,768。

### 实测结果

```
耗时 125s | 3 次调用 | 入 30,407 出 18,937
缓存命中 99%（30,080 / 30,407）          ← P-1/P-2 的核心验证
闸门全部通过，其中 26 条陈述落在期望区间 26–49
citation_issues 抓到真实错误：[P30] 标注页码 8，实际页码 7
重复告警：无 | 未覆盖：无
```

### 三个实测发现

**1. 缓存设计生效。** 99% 命中率 —— 布局反转（原文在前、指令在后）在真实提供商上成立。
提取与术语两次调用共享了同一份前缀。

**2. 机械闸门抓到了真实的页码幻觉。** 模型把 P30 标在第 8 页，实际在第 7 页。
`citation_issues` 闸门把它拦下，对应字段被清空 —— 不放行、不猜测。

**3. ⭐ 输出预算的假设错了一个数量级。**

26 条陈述实际消耗 **18,937 输出 token**（含推理思考），约 **573 token/条** ——
是可见载荷（64 token）的 **9 倍**。用 4096 预算时一条指令只能出约 5 条，
这正是首次真实运行直接撞 `OutputLimitError` 的原因。

**修复**：配额不再用常数，由输出预算推导：

```
配额 = max(4, ⌊max_tokens × 0.7 ÷ (64 × 9)⌋)

max_tokens    4,096 →   4 条/指令（自动拆成 13 条，按经验配额降低截断风险，仍需检查实际输出）
max_tokens   32,768 →  39 条/指令（1 条指令覆盖全文）
max_tokens  131,072 → 159 条/指令
```

用户确认 deepseek-v4.1-flash 输出上限 384K —— 容量完全不是瓶颈，
指令拆分仍同时受实际窗口、输出预算、推理消耗和注意力质量约束；该次容量信息不能作为通用保证。

### 遗留

- 复核链（语义复核）在真实模型上未跑通：推理模型单次调用超过 60 秒读取超时，
  需要把 `LITPRISM_REVIEW_READ_TIMEOUT` 提到 300s 并实测。
- 窗口 128k 是**假设值** —— 网关的 /models 没有报告该模型的窗口，需要在界面确认。
