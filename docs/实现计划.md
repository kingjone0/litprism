## 一、排序原则

```
第 1 优先  ████████  数据结构 + 不变量 + ref 系统
第 2 优先  ███████   上下文管理内核（Meter/Policy/Summarizer/Seam/恢复）
第 3 优先  █████     记忆系统（三层 + 不可变轮次 View）
第 4 优先  ████      内核增量（白名单/人工确认、Skill 框架、扫描件转写、交付物、MCP Server）
第 5 优先  ███       界面（三栏 + GenUI 渲染层）
第 6 优先  ██        外壳（Tauri + sidecar 打包）
```

**为什么这个顺序**：第 1–3 步做完，就能在 CLI 上跑通「导入 → 核验 → 解读 → 多轮问答 →
压缩 → 还原」的完整链路，且所有关键不变量都有测试覆盖。界面和外壳是包装，
放在最后不影响正确性，也避免在数据结构还在变的时候返工前端。

## 七、遗留分析：联网搜索是不是缺失的能力？

**结论：不是缺"网页搜索"，是缺"联网获取 → 核验 → 入库 → 回答"的编排。
这条链路已有约 70% 的组件，缺的是串起来的那一步。**

### 现状

| 环节 | 能力 | 状态 |
|---|---|---|
| 本地检索 | FTS5 BM25，问答证据来源 | ✅ |
| 学术检索 | Crossref / OpenAlex / arXiv / S2 | ✅（但只用于核验与推荐） |
| 真实性核验 | 多源交叉，五态判定 | ✅ |
| OA 全文定位 | Unpaywall | ✅ |
| 解析入库 | PDF / DOCX / HTML / TeX | ✅ |
| **编排** | 问题 → 检索 → 核验 → 下载 → 入库 → 回答 | ❌ **缺这一步** |

### 为什么回答不直接用网页搜索（这是设计，不是疏忽）

防幻觉三层防线的前提是：**所有进入上下文的证据都来自已核验的本地文献**。
通用网页内容无法通过这套核验 —— 把它混进证据，要么破坏引用回溯校验，
要么得给"网页内容"单开一个信任级别，而那个级别没有核验兜底。

### 正确的补法：网络只是获取渠道，不是证据来源

```
用户提问 → 库内检索不到足够依据
         → 用问题扩展检索学术数据库（已有：recommend / search_external）
         → 命中的论文走核验（已有）
         → OA 全文下载（已有 Unpaywall 定位，缺下载器）
         → 解析入库（已有）
         → 重新回答，引用照常校验
```

信任链完整：**回答的证据仍然全部来自已核验的本地文献**。
需要补的只有：① 问题触发的编排逻辑；② OA PDF 下载器；③ 下载前向用户确认（成本与相关性）。

### 通用网页搜索（Google/Bing/Tavily）——二期，且必须隔离

对背景知识、领域动态、工具文档有价值，但**不能与文献引用混排**：

- 独立的「网页来源」徽章与组件（视觉上与文献引用区分）
- 不进入 `[P#]` 引用校验体系
- 显式标注「来自网页，未经核验」

### 与 D3（扫描件转写）的关系

两者都需要"先有真实 Key 才能实测"，且都改变了**证据进入知识库的方式**
（扫描件：图像→文本；联网：网络→本地）。建议一起排在二期开头，
共用"导入前确认"这一交互。

## 八、阶段 F 进度

### F0 · sidecar 握手与 token 防护 —— ✅ 完成

| 文件 | 内容 |
|---|---|
| `src/litprism/sidecar.py` | Tauri sidecar 入口：握手协议 + token 中间件 |

**握手协议**：外壳以子进程启动 sidecar → stdout 打一行
`LITPRISM_READY {"port":…, "token":…}` → 外壳读行、把 token 经 IPC 注入前端 →
前端所有 /api 请求带 `X-LitPrism-Token` 头。

**为什么需要 token**：端口在 127.0.0.1 上，本机其他进程同样能访问。
一次性 token 保证只有经外壳启动的前端能用 —— 本地单机应用的最小访问控制。

**实测**（200/401/401，静态资源不设防）：

```
带 token      → 200
错误 token    → 401
无 token      → 401
静态资源      → 200（不设防，前端加载需要）
```

#### spike 抓出的真实缺陷：frozen 下所有路径落到 `%TEMP%`

**现象**：`/api/status` 的 `db_path` = `C:\Users\...\AppData\Local\Temp\data\litprism.db`。

**根因**：`PROJECT_ROOT = Path(__file__).resolve().parents[2]`。onefile 模式下 `__file__` 在
`_MEIPASS`（临时解包目录），于是 `./data` 与 `config/` 全部解析到临时目录 ——
用户装好用一周，数据可能被系统清理。连带 `config/` 未进 `datas`，用户配置生成不出来。

**修法**：拆成两个根，并抽纯函数便于测试：

| 根 | 源码 | frozen | 用途 |
|---|---|---|---|
| `BUNDLE_ROOT` | 项目根 | `sys._MEIPASS` | 只读资源（配置模板、static） |
| `APP_ROOT` | 项目根 | `%LOCALAPPDATA%\LitPrism` / `LITPRISM_HOME` | 可写（data、用户配置、密钥库） |

**验收（实测）**：db_path 落 `%LOCALAPPDATA%\LitPrism\data\`；用户配置生成于该目录；`GET /` 200、`/api` 无 token 401；**重启后 papers=1 chunks=61 仍在**。

**顺手修的两处**：握手行的 `pid` 原先写死 `null`，改为真实 PID；token 守卫只守 `/api`
（token 保护的是**数据**，不是界面外壳 —— 挡住 `/` 既不增加安全，又让打包版无法在浏览器排障）。

**新增测试** `tests/test_paths.py`（10 项）：模板只读、用户配置可写、`LITPRISM_HOME` 优先、
已存在的用户配置不被模板覆盖。全量 **506 项通过**。

**留给 F2**：Tauri 前端 origin 是 `tauri://localhost`，到 `127.0.0.1:PORT` 属跨源，
需加 CORS 或用 Tauri HTTP 插件 —— 尚未实测。

### F2 · 外壳工程 —— ✅ 完成（选定 Electron）

**结论**：外壳用 `desktop-electron/main.js`。Tauri 工程保留在 `src-tauri/` 作备选，
但当前环境跑不起来 —— **根因是这台机器 Chromium 的 GPU 进程以 `0xC0000005` 崩溃**
（`FATAL: GPU process isn't usable`），Tauri 的 WebView2 与 Electron 同一底座，都白屏。
Electron 加 `--disable-gpu/--disable-gpu-compositing/--disable-gpu-sandbox/--no-sandbox`
后正常渲染。
