# N09 配置与集成验收

日期：2026-10-24。基线提交 `936e8aa`，继承当前工作树的N04未提交增量，不覆盖它们；本轮未提交、push或打包。schema仍v15，无用户库或密钥迁移。

## 修复和当前契约

| 发现的问题 | 当前行为 |
|---|---|
| CLI直接build_llm、MCP启动时固定读取旧YAML模型，可能缺Key退mock | 与Web共用build_active_llm和同一数据根的ProviderStore；模型、协议、能力与SecretStore引用沿用当前选择。仅未选模型且显式mock配置允许离线占位；选中配置失效不退mock |
| MCP启动后切换界面模型仍用旧客户端 | 每次ask按当前选择构造客户端；只读检索不要求模型配置有效 |
| CLI init/config显示旧配置模型；config会暴露旧数据源Key | 另给当前选择的模型/协议/能力/缺配置原因，诊断同时遮蔽旧LLM与数据源Key；不修改原配置或凭据 |
| CLI mcp serve打印说明污染stdout，并重新加载配置 | 直接借用CLI已加载的cfg/kb；stdio stdout仅协议，错误在stderr，保留`--config`与数据根 |
| 模块入口不能指定配置；缺失指定路径可能落到另一工作区 | 模块支持`--config`。显式路径或LITPRISM_CONFIG不存在/不是文件时立即失败；显式空路径也不回落别库 |
| CLI ask的无效--paper会被过滤成全库 | 先校验指定论文；有未找到项就报错，不访问模型、不扩大范围 |
| 服务退出没有明确连接所有权；逻辑错误缺少协议标记/审计原因 | serve在退出时关闭自己创建的DB；借用CLI连接由CLI关闭。逻辑失败保留ok=false结构并标isError=true，审计记录失败原因 |

SDK仍为可选依赖：`pip install -e '.[mcp]'`，依赖范围2.x，本机实际验收SDK **2.3.0**。没有安装其他组件或修改全局Python环境。本机默认Python启动器失效时的兼容运行方法见AGENT。

旧直接`build_llm`库接口仍保留兼容行为，不表示新CLI/MCP允许绕过ProviderStore。原仅YAML/环境变量配置模型的用户须在同一数据根的Web设置中选择提供商和模型，不自动迁移明文Key或修改用户库。

## 入口能力差异

| 入口 | 来源/范围 | 恢复与人工知识路径 |
|---|---|---|
| 新Web聊天 | 默认相关全库可信材料/知识与实际联网摘要；主动限定则不扩范围 | chat_runs持久请求、显式续验、回复来源快照与右栏单元整理 |
| CLI ask | 本地可引用材料和已确认知识；--paper限定论文；无实时网页搜索 | 一次性内核问答，无持久Web请求/答后单元审核；调用失败不可假定精确恢复 |
| MCP ask | 全库本地可引用材料和已确认知识；当前无逐次论文范围参数或实时网页搜索 | 一次性内核问答，结构化状态/引用/用量与MCP审计；不自动获得Web持久恢复或人审入口 |
| MCP compare_papers | 返回当前已存分析的六维字段，不重新调用模型生成对比 | 与Web CompareAgent不同，不把旧材料分析作当前结论 |
| MCP import_paper | 默认不注册；显式读写模式仍核验，人工例外须给依据 | 不因注册写工具就自动取得可信状态 |

MCP的“只读”指不允许业务导入等写操作；启动可能建表/迁移，调用仍写审计，因此不是SQLite只读连接。验收只在新隔离根完成。

## 真实本地进程验收

工具 `tools/integration_acceptance.py --output _selftest.n09-integration-release-20261024` 使用两条明确标为测试的合成材料、真实本地HTTP服务、真实SDK客户端及服务子进程。它不读取用户配置/Key，子进程移除继承的模型Key与LITPRISM覆盖，显式指定隔离cfg/data；没有外部模型或搜索调用，也不是新的论文语义样本。

| 项目 | 实际结果 |
|---|---|
| Web/CLI/MCP × OpenAI/Anthropic | 六组合均正常问答；收到正确model与协议请求格式，均按已存1M/384000能力分配输出 |
| 同一MCP会话切换模型/协议 | 两种客户端按新选择调用，不用启动时旧模型 |
| 直接模块与CLI两种stdio入口 | SDK initialize、tools/list、tools/call、resources/read通过；CLI指定配置确实指向测试论文 |
| stdout与退出 | 三个会话子进程收到的16条stdout行全部可解析为JSON协议；三进程退出码均0。另两种入口空stdin/EOF均0且stdout为空 |
| 默认只读/显式读写 | 默认8工具、不注册import；读写模式9工具，但未核验导入被拒，材料仍仅2条 |
| 缺选择/密钥 | Web/CLI明确拒绝，MCP ask以isError和ok=false返回；检索仍可用，未新增模型HTTP请求 |
| 错误配置路径 | 模块退出2、CLI退出1，stdout为空；自动回归另检查未生成DB |
| 搜索缺Key、HTTP失败及错误schema | 缺Key为503；生产发现路径连接本机503桩后返回502，不新增来源；错误schema和密钥不泄露另有回归 |

协商协议版本为 **2025-11-25**，不表示已测试所有协议版本或宿主客户端。8次HTTP模型请求仅发向127.0.0.1（6qa＋2expand），并非8次付费API。16条协议输出分为直接入口10条、CLI入口3条、读写控制3条，stderr单独保留。初始和中间本机验收保留在各独立根，未覆盖；release根为CLI诊断遮蔽补齐后的最终源码，包含协议错误标记与搜索HTTP失败控制。

标准输出规则以[MCP stdio传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#stdio)为依据；SDK接口同时核对[官方Python SDK](https://github.com/modelcontextprotocol/python-sdk)和本机安装源码，实际结果以本轮记录为准。

## 接入方式

在项目已安装依赖的Python中，两个入口等价使用当前选择：

```powershell
$env:LITPRISM_HOME = 'E:/codex-litprism-data'
$env:PYTHONPATH = 'E:/codex-litprism/src'
# $py使用AGENT中的已验证Python；不要在此省略数据根。
& $py -m litprism.mcp.server --config 'E:/codex-litprism-data/config/config.yaml'
# 或：
& $py -m litprism --config 'E:/codex-litprism-data/config/config.yaml' mcp serve
```

当前机器若使用迁移后的WorkBuddy运行时，兼容启动方式如下；不会自动发模型请求，后续由MCP客户端调用工具：

```powershell
$env:LITPRISM_HOME = 'E:/codex-litprism-data'
$env:PYTHONPATH = 'E:/codex-litprism/src'
& 'E:/Program Files/WorkBuddyai/resources/vendor/python/python.exe' -c "import site,sys,runpy;site.addsitedir('C:/Users/18434/.workbuddy/binaries/python/envs/default/Lib/site-packages');sys.argv=['litprism.mcp.server',*sys.argv[1:]];runpy.run_module('litprism.mcp.server',run_name='__main__')" --config 'E:/codex-litprism-data/config/config.yaml'
```

宿主MCP配置中同样指定Python完整路径、上述模块/兼容参数、PYTHONPATH与LITPRISM_HOME；配置文件自身的data_dir也须指向该数据根，不能把另一工作树的相对配置当作隔离措施。stdio端口不占用HTTP监听端口，不在服务stdout粘贴说明或调试打印。
