## 〇·补、界面与扩展补充

### 第一轮补充（界面 + Skill/MCP 初稿）

- **顶层框**是 Tauri 无边框窗口的自绘标题栏，含侧栏开关 / 全局搜索 / 筛选 / 四个菜单，
  并**补上参考图中缺失的窗口控制按钮**（右侧，Windows 惯例）。
- **侧边栏**分「对话」与「知识库」两个区块；知识库为「分组 → 论文」树，
  支持重命名、拖动排序、右键菜单、批量操作、多格式导出。
- **重命名采用"显示名与原始题录分离"**（新增 `display_title` 字段）——
  否则会同时破坏核验比对、BibTeX 导出合规性与可恢复性。
- **设置页**七分区；模型配置页复刻参考图样式（提供商卡片 + 状态点 + 编辑/删除 + 添加），
  并补齐状态点三态语义、编辑弹窗字段。

### 第二轮修订（v2）

- **去除本地模型**：推理与嵌入全部走 API。理由 —— 本 Agent 的核心能力（多源核验）
  本就依赖联网，"离线可用"是伪需求；本地小模型做学术长文解读力不从心；
  去掉后安装包变小、设置页简化。
  **但 OCR 保留本地** —— 它是感知层（图像→文字），不是推理层，
  把整本书页面传到云端不合理；本机已有 `rapidocr-onnxruntime`。
  同时去掉「分场景默认模型」（全部用同一强模型，减少设计复杂度）。
- **新增右侧检视面板**，形成三栏：左栏「我在哪、有什么」，中栏「读、问、比」，
  右栏「什么关系、产出了什么」。右栏三个 tab：**图谱**（知识图谱 / 引用网络 / 时间线）、
  **交付物**（Agent 生成的综述草稿、对比报告、解读笔记、审稿意见）、
  **上下文**（选中对象的详情与核验证据）。
- **Skill 确认为内置固定**，不做开放插件体系；仅保留提示词模板可微调。
  一期只做「文献综述生成」「审稿人视角评估」两个。
- **MCP 改为「内核 + 适配层」架构**：内核是纯 Python 库，CLI / HTTP API / MCP Server
  是它的三个适配层。**内部调用直接走进程内函数，绝不走 MCP**（否则是自己给自己发请求，
  纯增加开销与失败点）。MCP 是**对外**接口 ——
  让 Claude Desktop、Cursor 等外部 Agent 能查询知识库、调用 `verify_paper` 防幻觉。
  **MCP Server 提到一期**（薄适配层，工作量小、价值高）；**MCP Client 放二期**。
- **新增数据表**：`collections` / `conversations` / `messages` / `deliverables` /
  `providers` / `mcp_servers` / `mcp_audit`。
- **API Key 不明文落盘**：用 Windows DPAPI 或 `keyring` 加密，数据库只存引用键。
- **本地能力边界明确**：解析/检索/图谱构建在本地；核验、解读、嵌入走网络。
  离线时只保留只读能力，并在界面明确提示。

### 第三轮修订（v3）

- ⭐ **扫描件改用多模态 API，推翻 v2 的"OCR 必须本地"判断**。
  依据是实测（`tools/ocr_probe.py`）：把有文本层的论文渲染成图再跑本地
  `rapidocr-onnxruntime`，字符相似度 0.92~0.97 看着不差，**但版面语义完全崩坏** ——
  双栏正文被拆碎（27 行 → 55 行），且 **Transformer 架构图里的图内标签
  （Softmax / Linear / Add & Norm）被当成正文混入文档流**。
  `rapidocr` 是"检测+识别"引擎，不做版面分析、不做阅读顺序推断、不区分图内文字。
  对学术论文（双栏+公式+图表+表格）而言，产出的是顺序错乱的文本碎片，会污染后续核验与引用定位。
  多模态模型把页面当整图理解，天然处理阅读顺序、版面语义、结构还原（直接输出 Markdown）。
  成本测算：一篇 15 页扫描件约 $0.08，75 页约 $0.40，个人一年约 $5 ——
  工业场景"成本扛不住"的论据针对的是日处理十万页，量级差三到四个数量级，不能直接套用。
  且只对**无文本层的页面**走这条路径，有文本层的直接解析（零成本零误差）。
- **Skill 框架降级为「内置任务模式」**：不定义 `skill.yaml`、不做加载器、不做可扩展机制，
  就是几段硬编码在 `prompts.py` 里的系统提示词 + 设置页可微调。新增两个：
  综述生成、审稿人视角。
- **MCP 规划定稿**：一期**只做对外的 MCP Server**，**不接入任何外部 MCP 服务**。
  逐项分析后结论是大部分候选价值可用原生实现替代且更简单 ——
  文件系统扫描就是遍历目录、Obsidian 输出就是写 Markdown、Zotero 用 BibTeX 覆盖约 80%。
  **MCP 真正的不可替代价值在于连接需要认证的第三方云服务**（如 GitHub），
  凡几行本地代码能做完的事，引入独立进程承担就是纯粹的复杂度负债。
  GitHub MCP 列为二期首要候选。**设置页不单开 MCP 分区**（一期只有 Server 一个开关，
  挂在「关于」页显示即可），二期引入外部服务时再独立。

### 第四轮修订（v4）—— 方案定稿

- **Skill 框架改为"建框架、不装内容"**：完整实现框架（清单规范、校验器、注册表、
  执行契约、设置页管理界面、测试夹具），但**一期不内置任何 Skill** ——
  包括不添加 v3 提过的「文献综述生成」「审稿人视角评估」。

  这个顺序是刻意选的：框架是架构决策、内容不是，扩展点形状定错了后面每加一个 Skill
  都要绕；空容器还能真实验证"扩展点够不够用"——只在自写 Skill 上验证过，
  容易把"恰好够用"当成"足够通用"；验证则改用测试夹具（临时目录构造 Skill），
  不依赖内置 Skill，避免测试与业务耦合。

- **Skill 框架的两条硬边界**：
  ① **仅声明式**，不支持自定义代码 —— 允许携带可执行代码等于开放任意代码执行入口，
  用户从别处拿来的 Skill 就能在你机器上跑任意逻辑，要支持必须先有沙箱方案；
  ② **防幻觉约束不可绕过** —— 全局学术规范由框架强制前置，`citation_required` 时
  引用回溯校验由框架执行，不依赖 Skill 作者自觉。
  用户自行添加的 Skill 是系统里最不可信的输入源，能绕过约束的话前三层防线就白建了。

- **区分"内核能力"与"Skill"**：结构化解读、术语解释、问答、对比、查询扩展是**内核能力**
  （硬编码在 `prompts.py`，仅可查看与微调），**不是 Skill**；Skill 是用户自行添加的扩展，
  一期为空。

- 设置页分区确定为九个：通用 / 模型 / 数据源 / 核验与白名单 / 检索 / 提示词 / **Skill** /
  导出 / 关于。

**至此方案完整，等待开工许可。**

### 第六轮修订（v6）—— 上下文管理与记忆系统

用户提供了两份高质量参考（《Agent 框架上下文管理设计参考》与
《DSH 与 billion-context 上下文管理机制》）以及 `dsh-mnemon`。
据此新增 `上下文管理与记忆系统设计.md`，替换掉此前过于简略的上下文/记忆设计。

⭐ **最重要的收获是一条核心判据**：

> **每一次压缩，是在「窗口位置」上动手，还是在「新增量」上动手？**
> 窗口位置 = 阈值到了就重写历史 → 前缀作废、损失随轮次复利衰减、单粒度、模型无参与。
> 新增量 = 只压「上次压缩之后新增、且已被任务消费掉」的部分 → 前缀不变、
> 每份内容一生只折一次、可分级、模型可参与。

**LitPrism 取后者**，且我们的场景有天然优势：**"已消费"的边界是清晰可判的**
（一轮问答结束后该轮检索到的片段即已消费），不像编码 agent 要靠工具配对判断工作集边界。

**上下文管理照抄的四个架构决定**：append-only transcript + 派生视图；
单一测量服务；摘要后端可替换；单一写入口 + 前置不变量。

**LitPrism 的两个特化设计（重要）**：

1. ⭐ **`chunks` 表就是内容寻址存储**。论文原文本来就在 SQLite 里且有稳定 `chunk_id`，
   所以压缩时**不需要把原文塞进摘要** —— 直接记句柄，需要时一条 SQL 取回。
   这是相对通用 agent 的结构性优势：**原文从未真正离开系统**。
   由此免费拿到参考文档所说的 L2 级可逆性。
2. ⭐ **引用片段：正文可折叠，句柄（chunk_id/page）永不折叠**。
   防幻觉要求引用可追溯，压缩不能破坏这个。句柄体积极小，正文按需取回。
   并新增一条不变量：**压缩不得改变引用校验的结论**。

**明确砍掉的部分（及理由，避免后人误以为漏了）**：tier-2/3 多代分级（会话长度不足以触发）、
漂移重锚（我们完全控制消息序列化，不适用）、双压缩冲突检测（只有一套压缩器）、
完整 miss 三类归因（单机低频，收益不抵复杂度）。

**记忆系统**：映射 `dsh-mnemon` 的三层 —— 常驻层（偏好，≤500 token 硬上限）、
按需层（笔记/交付物）、事实层（**知识库本身就是 Memory Space**，不需要再建平行存储）。
每轮检索结果固化为**不可变 View** 并 pin 到该轮（一致性 + 可审计 + 可复现）。
一期只做**显式写入**，不做隐式推断。

⭐ **信任模型比 `dsh-mnemon` 更强一层**：它要求"记忆历史不凌驾于当前指令之上"，
LitPrism 要求 **"记忆不得凌驾于防幻觉约束之上"** ——
记忆只能影响表达偏好，不得作为引用来源，不得改变核验结论。
理由：记忆是"用户说的"不是"文献说的"，混淆两者等于新开一条更隐蔽的幻觉通道。

## 一、目标架构

```
┌──────────────────────────────────────────────────────────┐
│  Tauri 外壳（Rust）—— 新增                                │
│  · 窗口 / 托盘 / 菜单 / 通知 / 自动更新                     │

│  · sidecar 进程生命周期管理、单实例锁                        │
└───────────────┬──────────────────────────────────────────┘
                │ ① spawn sidecar，读取握手信息
                │ ② 通过 IPC 把 {端口, 一次性 token} 交给前端
                ▼

│  Web 前端（复用现有界面，拆分为模块）                        │

                │ Authorization: Bearer <一次性 token>
                ▼
┌──────────────────────────────────────────────────────────┐
│  Python Sidecar（PyInstaller 单文件，现有 FastAPI 后端）    │
│  ├─ 已实现：解析 · 章节识别 · 分块 · 题录补全 · 多源核验      │
│  │          结构化解读 · 术语 · 跨论文关联 · 问答 · 对比 · 推荐│
│  └─ 一期新增：人工确认放行 · 模型管理 API                    │
└───────────────┬──────────────────────────────────────────┘
                │
      ┌─────────┴──────────┐
      ▼                    ▼
  本地数据              外部服务
  SQLite 知识库          Crossref / OpenAlex / arXiv
  （新增白名单表）        Ollama（本地模型）
```

### sidecar 通信协议（一期实现要点）

1. Rust 侧 `spawn` sidecar 可执行文件；
2. sidecar 启动时绑定 `127.0.0.1:0`（由 OS 分配空闲端口），生成一次性随机 token，
   把 `{"port": <n>, "token": "<hex>"}` 以**单行 JSON** 写入 stdout；
3. Rust 读取首行并解析，通过 Tauri IPC 把两者交给前端；
4. 前端所有请求带 `Authorization: Bearer <token>`，后端校验；
5. **防残留**：Rust 监听窗口关闭 / 退出事件并 kill sidecar；sidecar 侧同时做父进程存活检测
   （周期性检查 stdin 是否 EOF），任一侧异常退出都能清理；
6. **单实例锁**：Rust 侧用命名互斥体防止重复启动导致端口与数据库冲突。

> 为什么不用"固定端口"：固定端口会与其他软件冲突，且暴露面更大。
> 随机端口 + 一次性 token + 仅监听回环地址，是本机场景下够用且简单的方案。

| 模块 | 新增内容 |
|---|---|
| `db.py` | 新增 `whitelist` 表；`papers.verify_status` 增加 `manual_confirmed` 取值 |
| `verify.py` | 核验判定从四态扩展为**五态**（见下）；核验前先查白名单，命中则直接放行并标注来源 |
| `agents.py` | 问答/对比中标注每条证据的核验来源（自动核验 / 人工确认），两者用不同徽章区分 |
| `cli.py` | 新增 `whitelist list/add/remove` 子命令，保证 CLI 与桌面端能力对齐 |

**五态核验判定：**

| 判定 | 含义 | 允许引用 |
|---|---|---|
| `verified` | 自动核验通过（DOI 精确命中或相似度 ≥ 0.92 + 佐证） | ✅ |
| `manual_confirmed` | 自动核验未通过，但**用户人工确认**并留痕 | ✅（徽章与 `verified` 区分） |
| `likely` | 疑似匹配，待用户处理 | ⏸ 挂起，等待确认 |
| `not_found` | 数据库正常响应但无匹配 | ❌（可申请人工确认） |
| `unchecked` | 数据源全部失败 | ❌（可重试，不建议直接人工确认） |

**白名单数据模型：**

```sql
CREATE TABLE whitelist (
  id                      TEXT PRIMARY KEY,
  paper_id                TEXT,
  doi                     TEXT,
  title                   TEXT NOT NULL,
  level_at_confirm        TEXT,   -- 确认时的自动核验判定，保留原始结论
  verify_evidence         TEXT,   -- 确认时的核验证据快照（JSON），可追溯
  reason                  TEXT,   -- 用户填写的确认依据，必填
  confirmed_at            TEXT,
  confirmed_by            TEXT
);
```

> 设计要点：白名单**不覆盖**而是**并存**于自动核验结论。
> `papers.verify_level` 记录人工确认后的状态，但 `verify_evidence` 里保留"自动核验当时判定为 not_found"
> 这一事实。这样将来复核时能看出"哪些是机器判定的，哪些是人拍的板"，不会把人的判断伪装成机器的结论。

### 3.2 模型管理模块（一期）

### 3.4 前端重构

- 新增两个页面：**核验确认页**（展示候选匹配与证据，填写确认依据）、**模型管理页**；

  —— 打包后的桌面应用可能在无网环境运行。

## 五、风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Rust 工具链未装，MSVC Build Tools 体积大、安装耗时 | 阻塞一期启动 | 作为第一步单独执行并验证 `cargo build` 能通过 |
| PyInstaller 打包 pymupdf 原生库失败 | 阻塞打包 | 一期早期先做一次最小打包验证（spike），不等到最后 |
| 双进程生命周期管理复杂（残留、端口、崩溃） | 体验问题 | 双向存活检测 + 单实例锁 + 启动失败时给可读错误 |
| Tauri 首次构建耗时长 | 开发迭代慢 | 开发期用 `tauri dev` 热重载；sidecar 用脚本启动而非每次重新打包 |
| 人工确认被滥用成"万能放行" | 削弱防幻觉价值 | 确认依据**必填**；保留自动核验原始结论；徽章明确区分；提供白名单审计视图 |
| 二期 OCR / embedding 依赖体积膨胀 | 安装包变大 | 评估按需下载；或提供"精简版 / 完整版"两种安装包 |
