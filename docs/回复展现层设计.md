# 文献棱镜 LitPrism · 回复展现层设计（生成式 UI）

> 参考 `dsh-genui` 的生成式 UI 思路，设计聊天回复的展现方式。
> **上下文管理与记忆系统已独立成文**：见 `上下文管理与记忆系统设计.md`。
> 日期：2026-10-16 · 状态：待确认

---

## 一、为什么适合这个场景

论文解读的输出**本身就是结构化的** —— 六个固定维度、对比矩阵、术语表、核验状态、
引用片段。用纯 Markdown 呈现，读者要在长文本里自己找结构；
用生成式 UI 直接渲染成卡片/表格/徽章，信息密度和可读性都会明显提升。

参考 `dsh-genui` 的核心思路：**模型输出 JSON 描述界面，客户端白名单渲染成组件，
边生成边出现，交互事件可回传模型**。这个模式可以直接借鉴，但组件集要按学术场景重做。

## 二、围栏协议

模型在回复中用 `lit-ui` 围栏输出 JSON：

````
下面是该论文的解读：

```lit-ui
{
  "v": 1,
  "type": "analysis",
  "paper_id": "p_58306504ca1d",
  "fields": [
    {"key": "research_question", "text": "序列转导模型依赖复杂的循环或卷积网络…… [P1 p.1]"},
    {"key": "methodology", "text": "提出 Transformer，完全基于注意力机制…… [P2 p.2]"}
  ]
}
```

以上解读仅基于原文片段。
````

**关键**：组件**嵌入**在回复里，**不替换周边文本**。文字分析保留，UI 与之并排呈现。

## 三、组件白名单（学术场景定制）

| 组件 | 用途 |
|---|---|
| `paper-card` | 单篇论文卡片：题录 + 核验徽章 |
| `paper-list` | 论文列表（检索/推荐结果） |
| `analysis` | 结构化解读（六维度） |
| `comparison-table` | 多篇对比矩阵 |
| `concept-list` | 术语表 |
| `citation-list` | 引用片段（可展开原文） |
| `verify-result` | 核验结果（四态 + 候选匹配 + 证据） |
| `graph` | 知识图谱（节点-边） |
| `timeline` | 领域演进时间线 |
| `table` / `chart` | 通用表格与图表 |
| `tabs` / `accordion` | 分组容器 |
| `callout` | 提示块（用于区分"原文事实 / 作者主张 / 模型推断"） |
| `form` | 表单（核验确认、参数输入） |
| `progress` | 进度（批量导入、扫描件转写） |

统一信封：`{"v": 1, "type": "<组件>", ...组件字段}`。
完整字段规范单独维护（`docs/lit-ui-schema.md`，实现阶段产出）。

**一期先做核心 8 个**：`paper-card` / `paper-list` / `analysis` / `comparison-table` /
`concept-list` / `citation-list` / `verify-result` / `callout`。
其余视实现进度排入一期或二期。

## 四、渲染链路

```
模型输出 lit-ui 围栏 (JSON 界面描述)
        ↓
前端渲染器识别围栏语言
        ↓
白名单组件渲染 → 内联出现在回复中（流式：组件一完成就出现，不等整条回复写完）
        ↓
用户交互 → 本地即时处理 或 事件回传（闭环）
```

**流式要求**：第一个完成的组件立即渲染，不必等整条回复结束。
对长解读（六个维度）体验差别很大。

## 五、与防幻觉的关系（本设计的核心约束）

**UI 是呈现层，不能成为绕过校验的通道。** 具体三条：

### ① 引用校验照常执行

校验器扫描**所有文本字段**中的 `[P1 p.3]` 标记，规则与纯文本问答完全一致。
组件化不改变校验逻辑。

### ② 核验徽章由框架注入，不接受模型输入

`paper-card` / `paper-list` 里的核验状态，**不由模型填写**。
模型只能提供 `paper_id`，框架查数据库填充真实状态。

> 否则模型可以把一篇 `not_found` 的论文渲染成"✅ 已核验"——
> 这就等于在 UI 层开了个后门，把第三层防线的价值抹掉。

### ③ 引用页码由框架注入，不接受模型输入

`citation-list` 里的页码、章节、原文，**由框架根据 chunk_id 从数据库取出**。
模型只能给 chunk_id。

> 这一条直接堵死了"页码编造"这个幻觉通道 ——
> 模型连编页码的机会都没有，因为它根本不用填页码。

**结论**：生成式 UI 不但不削弱防幻觉，反而**多了一层结构性保障** ——
把原本靠模型自觉的字段，改成框架注入。这是纯文本渲染做不到的。

## 六、安全与健壮性

借鉴 `dsh-genui` 的做法，按本项目情况调整：

| 规则 | 说明 |
|---|---|
| 白名单组件 | 模型无法注入 HTML / 脚本 |
| 禁用 eval | 函数表达式走独立解析器 |
| 节点上限 | 200 节点 / 8 层嵌套 |
| 字段截断 | 单文本字段 ≤ 4000 字符，超长截断 |
| 数字钳制 | 数值字段做范围限制 |
| 单点失败隔离 | 坏节点静默丢弃，兄弟节点继续渲染 |
| 诚实交互 | 无 `action` 的交互元素渲染为**禁用**，杜绝假按钮 |
| 不索取机密 | 绝不出现 API Key / 密码类输入框 |

## 七、降级策略（必须有）

**绝不出现空白。** 逐级降级：

```
围栏 JSON 解析失败        → 回退为纯 Markdown 渲染该段
单组件渲染失败            → 该组件降级为纯文本块，其余继续
整条回复渲染异常          → 显示原始 Markdown + 可折叠的原始 JSON（便于排查）
模型未输出围栏            → 就是普通 Markdown 回复，一切照常
```

**模型侧的自愈**：围栏渲染失败时，在同一回合内用逐节点诊断引导模型重发修正围栏，
每回合最多 2 次纠正（参考 `dsh-genui` 的做法）。
