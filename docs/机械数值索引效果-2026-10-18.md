# 机械数值索引的实测效果

2026-10-18。评估「复活 value_index」能带来什么、不能带来什么。
配套原型：`tools/proto_numeric_index.py`（零模型成本，只测量，未接入生产）。

---

## 1. 背景：value_index 目前是死的

`reconcile()` 里有一段确定性数值比对：

```python
groups[(paper_id, subject, metric, conditions)].append(fact)
if len({value|unit for fact in facts}) > 1:  → 报冲突
```

但 `facts` 只从 `review['facts']` 来，而 `REVIEW_SYSTEM` 第 31 行明确写着
`do not ... extract numeric facts`。新协议从不返回该字段，于是 `unit['facts']` 恒为 `[]`，
这段代码**永不触发**。

「简化协议以免输出预算耗尽」和「数值冲突用机械比对」这两个决定互相打架，
后者的前提被前者顺手拆掉了。

---

## 2. 第一版设计失败：按"指标短语"分组

最初想抽 `(指标短语, 数值, 单位)` 三元组，按指标分组。实测直接崩：

| 原文 | 抽出结果 | 问题 |
|---|---|---|
| `SuperGLUE Average 为 71.8` | 指标被停用词"为"吃空 → 整条丢弃 | 指标抓不到 |
| `GPT-3 Few-Shot` | `metric=gpt, value=3` | 模型名被当成数值 |

根本原因：**机械方法拿不到 subject / metric / conditions**，而这正是模型抽 facts 才有的东西。

## 3. 改用「子句签名」

不做语义理解，只判断**两句话的结构是否同构**：

1. 按 `，。；、` 切子句；
2. 把子句里的数字遮成 `#`，归一化成签名；
3. 签名相同的子句视为"在说同一件事"，比数值序列；
4. 序列不同 → 冲突候选（沿用现有的 `needs_review` 语义，不直接判错）。

```
"GPT-3 Few-Shot 的 SuperGLUE Average 为 71.8，RTE Accuracy 为 69.0"
"GPT-3 Few-Shot 的 SuperGLUE Average 为 69.0，RTE Accuracy 为 71.8"
        ↓ 签名相同，数值序列 (3,71.8) vs (3,69.0) / (69.0) vs (71.8)
        → 报冲突 ✅（列错配被抓到）
```

---

## 4. 实测结果（18 条固定集）

| 指标 | 结果 |
|---|---|
| 含数值的陈述 | **10/18（56%）** —— 机械层的覆盖上限 |
| 冲突组 | **3 组，全部为真实冲突，零凭空报警** |
| 数值型负例召回 | **2/2（100%）** |
| 语义型负例召回 | **0/7（0%）** |
| 正例被卷入 | 2 条，均为冲突对的**正确一侧**（不是误报） |

被抓到的两条：

- `superglue-column-negative`：Average 71.8↔69.0、RTE 69.0↔71.8 的**列错配**
- `fasttext-classes-negative`：`312K 个类别` vs `312 个类别` 的**量级错**

抓不到的 7 条，全部是语义型错误：

| 类型 | 例子 | 为什么抓不到 |
|---|---|---|
| 条件错 | 20.50 是 zero-shot，被写成 few-shot | 数字相同，错在设置 |
| 方向错 | "达到 20.50" 写成 "提高到 20.50" | 数字相同，错在动词 |
| 指标错 | "减少运行时间 7–64%" 写成 "提高准确率 64%" | 指标不同，签名不同 |
| 术语对调 | re-centering ↔ re-scaling | 无数字 |
| 否定/量化 | "从 p% 估计" 写成 "必须使用全部输入" | 无数字 |
| 实体错 | CPU → GPU | 无数字 |
| 限定词错 | "常与…相当" 写成 "所有任务都超过" | 无数字 |

---

## 5. 结论：它值不值得做

**值得，但要摆正定位 —— 它是覆盖率工具，不是成本工具。**

### 真实收益：长论文的确定性兜底

| | 模型语义层 | 机械数值层 |
|---|---|---|
| 240 条长论文覆盖 | **0/6 字段（实测）** | **全部含数值陈述（约 56%）** |
| 成本 | 40 次调用 × 2600 token | 0 |
| 确定性 | 依赖模型 | 可复现 |

长论文的语义层目前一条字段都核不完，而数值错误恰恰是**最伤人的一类**
（写错实验数字比措辞偏差严重得多）。机械层能让这类错误**在任何长度的论文上都 100% 覆盖**。

### 不要指望它降成本

它不会减少模型调用次数：数值没有冲突的陈述对，仍需要模型判断是否存在语义冲突。
所以"省预算"是伪收益，**"补覆盖"才是真收益**。

### 能力边界（必须写进界面）

- 只能抓**同构子句内的数值差异**；
- 改写/同义表达会漏（签名不同）；
- 条件、方向、限定词、实体错误**一律抓不到**，这些只能靠语义层或人工。

因此界面文案不能写"已核验数值"，只能写「数值一致性已机械比对」，
且未命中的部分仍标「待人工核对」。

---

## 6. 落地建议

1. **抽取放在 `make_units` 阶段**，与陈述同时生成，不额外调用模型；
2. **冲突候选并入现有 `differences`**，`method='clause_signature'`，`status='needs_review'`
   —— 不新增状态，不改 `coverage` 语义；
3. **条件词命中时降级**为 `condition_dependent`，只提示不判错；
4. `coverage` 增加 `numeric_pairs_checked` 计数，让"机械层跑了多少"可核对；
5. 保留模型 facts 通路（`_facts`）不动 —— 将来若恢复抽取，两条路可叠加。

预计改动：`semantics.py` 约 60 行 + 单测 15 条，不涉及协议与提示词变更。
