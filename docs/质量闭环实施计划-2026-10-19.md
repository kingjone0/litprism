## 三、N05 漏提补录

### 目标
让人从原文补入机器未提出的陈述，并与机器结果**分开记录**。

### 改动点

| 层 | 改动 |
|---|---|
| schema v11 | 新表 `manual_claims(id, paper_id, analysis_hash, field, text, chunk_id, page, quote, note, created_at)`；不复用 `semantic_reviews`（那是裁决，这是采集） |
| 后端 | `POST /api/paper/{pid}/semantic/claims`（field/text/chunk_id/quote）；`GET .../semantic` 的 items 增加 `origin: machine\|manual` |
| 校验 | `quote` 必须能在 `chunk_id` 原文里逐字找到；`chunk_id` 必须属于该论文；`analysis_hash` 必须匹配当前分析 |
| 前端 | 右栏「补一条」：从原文选中句子 → 选字段 → 预览 → 保存；列表里人工条目用不同标记 |
| 指标 | `eval_extraction.py` 增加已采集漏提占比（兼容键 `recall = manual / (machine + manual)`），未采集时仍显示 `n/a` |

### 验收标准
1. 补一条后，已采集漏提占比在两边都有数据时从 `n/a` 变成具体数字，且分母写明"机器 N + 人工 M"；
2. 人工条目**不**自动获得 `machine_supported` 状态，也不自动入库；
3. `quote` 与原文不匹配时拒绝保存，并指出第一个不匹配位置；
4. 换一版分析后，旧的人工条目仍可查看但标记"属于旧版本"。

### 风险
- **人为凑数**：补录必须绑原文引用，无引用的直接拒绝 —— 这条不能放宽。
- 补录条目参与已采集漏提占比分母，会让人有"少补 = 指标好看"的动机。口径上必须同时展示**人工补录绝对数**，不能只报比例。

### 落地记录（2026-10-19）

| 项 | 实现 |
|---|---|
| schema **v11** | `manual_claims(id, paper_id, analysis_hash, field, text, chunk_id, page, quote, note, created_at)` + 版本索引 |
| 校验 | 字段白名单、文本 ≤2000、引用必须**逐字**出现在该 chunk（折叠空白后比较，容忍 PDF 断行）、chunk 必须属于该论文、`analysis_hash` 必须匹配 |
| API | `POST /api/paper/{pid}/semantic/claims`、`DELETE .../claims/{cid}`；`GET .../semantic` 增加 `manual` 与 `recall` |
| 界面 | 右栏「人工补录」卡片：列表 + 删除 + 「补一条」表单（字段、原文块、选中文字作为引用、陈述内容） |
| 评测 | `eval_extraction.py` 的漏提采集行从写死 n/a 改为按 `manual_claims` 计算 |

**口径修正（实测发现）**：首版 `ratio = manual / (machine + manual)`，在
`machine=0, manual=1` 时算出 **100%** —— 但机器根本没产出陈述，那不是"全漏了"，
而是没有分母。已改为**两边都有数才给比例**，否则 `None` 并说明缺哪一边。
界面显示 `n/a`，不会因为 `pct(null)` 而渲染成 0%。

测试：`tests/test_manual_claims.py` **20 项**（校验、去重、版本隔离、删除、漏提采集口径、API）。
当时全量 **886 项通过**。

## 四、N06 质量面板

### 目标
把已有审核记录与 N05 补录聚合成一个可读的面板，**分字段**。

### 改动点

| 层 | 改动 |
|---|---|
| 后端 | `GET /api/paper/{pid}/quality`：按字段返回 `total / reviewed / verbatim / corrected / rejected / manual / recall` |
| 前端 | 论文详情页一个面板：字段 × 指标表格 + 覆盖率进度条 |
| 空状态 | 无审核记录时显示"尚无人工审核，指标不可用"，不显示 0% |

### 验收标准
1. 分字段展示，不合并成单一总分（总分掩盖"局限"字段 20% 这类问题）；
2. 同时显示**分母**：已审 / 总数；
3. 漏提未采集时显示 `n/a`，不显示 0；
4. 面板数字与 `eval_extraction.py` 对同一份数据的结果一致（同源计算，不各写一套）。

### 落地记录（2026-10-19）

| 项 | 实现 |
|---|---|
| 共享聚合 | 新增 `src/litprism/quality.py`；`tools/eval_extraction.py` 改为调用它，**只剩一套口径** |
| API | `GET /api/paper/{pid}/quality` 返回 `fields[] / totals / has_data / note / definitions` |
| 界面 | 论文详情「质量面板」：字段 × 11 列，合计行加粗；无数据时隐藏表格并显示原因 |
| 联动 | 补录新增/删除后同时刷新质量面板（否则表里数字是旧的） |

**实测（临时库，6 条机器陈述 + 4 条审核 + 2 条补录）**：

| 字段 | 陈述 | 已审 | 逐字 | 修正 | 拒绝 | 补录 | 逐字精度 | 可用率 | 覆盖 | 已采集漏提占比 |
|---|---|---|---|---|---|---|---|---|---|---|
| 关键结论 | 3 | 3 | 1 | 1 | 1 | 1 | 33% | 67% | 100% | 25% |
| 方法论 | 2 | 1 | 1 | 0 | 0 | 0 | 100% | 100% | 50% | n/a |
| 局限与未来工作 | 1 | 0 | 0 | 0 | 0 | 1 | n/a | n/a | 0% | 50% |
| 合计 | 6 | 4 | 2 | 1 | 1 | 2 | 50% | 75% | 67% | 25% |

⭐ **口径细节**：`覆盖` 的分母是"陈述总数"，非零就给数字 ——
"6 条里 0 条审过"是确凿的 0%；而 `精度` 的分母是"已审数"，
没审过时不可知，必须是 `None`。两者不能混为一谈。

测试：`tests/test_quality.py` **19 项**。当时全量 **905 项通过**。

## 五、N12 原文块版本化

### 目标
同一篇论文再次导入时，新旧原文不混在一起。

### 改动点

| 层 | 改动 |
|---|---|
| schema | 新表 `materials(id, paper_id, source, origin, content_hash, imported_at, level, status)`；`chunks` 增加 `material_id` |
| 导入 | `add_paper`/`add_chunks` 先建 material，再挂 chunks；`find_duplicate` 命中时返回已有 id 与材料版本 |
| 策略 | 导入时由调用方选择 `replace`（默认）或 `keep_both`；`replace` 旧 material 标 `superseded`，不物理删除 |
| 引用 | `analyses` 记录所用 `material_id`；旧分析的引用仍指向旧 material |
| 查询 | 默认只取 `current` material 的 chunks；`kb.get_chunks(paper_id, material_id=None)` 向后兼容 |

实际 N12 包含原子迁移、材料切换、历史分析归档和幂等规则；下表为原方案摘要，最终实现见 [N12 契约](N12原文材料版本化-2026-10-20.md)。

### 验收标准
1. 同一论文导入两次后，`get_chunks` 默认只返回当前版本（低完整度或历史内容重试不会覆盖当前全文），块数不翻倍；
2. 旧分析的引用仍能解析到旧 material，不报"来源失效"；
3. `replace` 后 `papers.material_level` 只升不降的规则仍然成立。

### 风险
- 这是**破坏性 schema 变更**，必须先在临时库上跑迁移 + 全量测试，不能直接动主库。
- 旧分析不自动重写（沿用现有约定），但要能看出它基于哪一版材料。

## 六、N08 备份与恢复

### 目标
能整库导出、校验、恢复；失败可回滚。

### 改动点
- 导出：`litprism.db` + 可选原文 PDF + 清单（papers / 审核记录 / 产出 / 偏好计数）+ SHA256 校验
- 恢复：先预检（schema 版本、必需表、校验和）→ 写入新目录 → 校验 → 切换；失败保留原库
- 密钥**不随库迁移**：DPAPI 密文跨机器不可解，恢复后要求重新填 Key 并明确提示

实际恢复仅接受同 schema 的备份并写入新目录，之后由用户安排重启切换；完整文件范围、限制和验收见 [N08 契约](N08备份恢复与目录迁移-2026-10-20.md)。

### 验收标准
1. 导出→恢复→再导出的逻辑 `content_hash` 一致；各自 ZIP 物理文件 SHA-256 独立校验，不要求 SQLite 文件字节一致；
2. 恢复中断不会留下半套数据（要么完整切换，要么原库不动）；
3. 密钥缺失时明确提示"需要重新配置"，不静默用 mock。

## 七、N07 策略 A/B（已取消）

2026-10-20 决定：**不再比较 `whole` 与 `batched`，分批不再作为设计选项。**

理由不是"分批不好用"，而是**它没有存在的前提**：

1. **单篇论文装得进窗口**。当前生效模型的能力是 1M 窗口 / 384K 输出，而一篇论文
   （即使 100 页综述）也就几十万 token 量级；按实测，fastText 5 页 = 3.7k token，
   线性外推 100 页 ≈ 75k，距 1M 有一个数量级的余量。也就是说"整篇装不下"在现役模型上
   不会发生，为它设计的退化路径只是凭空多一条分支。
2. **没有模型配置就不该解读**。未选模型时窗口与输出能力都未知，解读只会在半盲状态下烧时间，
   所以真实入口一律报错要求先选模型（`build_llm` 返回 400），而不是退化成某一档默认值硬跑。
   这与"不编"的底线一致：宁可拒绝，也不假装能跑。

因此本节的样本、口径与验收标准一并作废；质量结论只走第八节的整篇验收。
`plan.py` 里"超出窗口 → 分批"的分支保留为**防御性代码**（不删，但不再是设计目标，
也不设 A/B、不进入任何结论）；若真被触发，说明模型能力或材料规模超出预期，应当拒绝解读而不是默默降级。

## 八、整篇长论文验收（2026-10-20 实测）

样本：arXiv 2312.10997（RAG 综述，21 页，fulltext）。

### 三次实测对照

| 项 | ① 单条指令 | ② 配额上限 24 | ③ 大纲分节 + 有界对话 |
|---|---|---|---|
| 分块 / 指令 | 105 / **1** | 153 / 7 | 152 / **5** |
| 陈述 | 19 | 66 | **67** |
| 实验设计 | **空** | 4 | 4 |
| 研究问题 / 方法 / 结论 | 3 / 6 / 6 | 3 / 32 / 19 | 7 / 21 / 30 |
| 覆盖 | 缺 1 段 | 缺 4 段 | 缺 **2** 段 |
| 调用 | 8 | 25 | **18** |
| 输入 / 输出 | 104k / 26k | 788k / 201k | **512k / 104k** |
| 缓存命中 | 95% | 88% | **97%** |
| 耗时 | 2m30s | 16m39s | **10m36s** |

读法（别只看条数）：

- ②→③ 的成本下降要算准：**单次请求没变小**（每次输入 39,021 → 38,895），
  省的是**调用次数**（提取 16 → 9）。全文前缀在 whole 模式下每次都照发，靠相同前缀吃缓存。
  调用次数下降的主因是**大纲分节**（7 条按配额硬切的指令 → 5 条章节指令），
  不是有界对话。
- **有界对话在 token 上几乎不省钱**（每条指令只多几行概要），它的价值是跨章一致性；
  把它当省钱手段是错误归因。
- ③ 的章节是 PDF 大纲给的（5 条指令 = 7 个真实章节，References 已排除），不再是靠配额硬切。
- 「创新」只有 1 条**不算缺陷**——综述的创新通常是一套分类法或框架，条目天然少；
  评价要按论文类型读，不能拿研究论文的条数当基线。

#### 覆盖缺 2 段？逐段核对后只有 1 段是真缺

把每条指令的原文块与全部 67 条陈述的引用标签做交集：

| 指令 | 范围 | 块数 | 被引用的陈述 |
|---|---|---|---|
| d1 | Introduction、Overview of RAG | 23 | 16 |
| d2 | Retrieval 第 1/2 段 | 26 | 17 |
| **d3** | **Retrieval 第 2/2 段** | **13** | **0** |
| **d4** | **Generation、Task and Evaluation** | **25** | **15** |
| d5 | Discussion、Conclusion | 16 | 19 |

- **d4 是误报**：它的 25 块被 15 条陈述引用，内容已经进来了，只是该单元的字段检查没过关。
- **d3 是真缺**：Retrieval 后半段 13 块没有任何陈述引用，确实没读到。

因此代码改为把两种情况分开记录：`uncovered_units`（完全没有产出）与 `flagged_units`
（有产出但未通过闸门）。`complete=False` 仍然两者都触发，但报告不再把"有内容"的段说成"未覆盖"。

#### d3 那 13 块是什么内容

逐块看过（p8–p9，Retrieval 后半段）：查询优化（Multi-Query、Query Rewrite、Step-back、HyDE）、
embedding 微调与外部适配器（REPLUG、UPRISE）——**是实打实的方法细节，本该产出陈述**。

闸门记录给出直接原因：

```
section_coverage: 提出 0 条，期望 7–14 条 —— 疑似漏读
citation_issues : 模型返回未知字段或结构损坏，本批字段未放行；请核对原始响应
```

即**该批响应结构损坏被整批拒收**，不是"这段没有可提取内容"，也不是模型判定它无关。
修复轮没有救回来，说明修复提示对"结构损坏"这一类无效（它按字段缺失设计）。

改进（2026-10-20 已实施）：

1. **结构损坏走独立重试**：不再复用"补字段"的修复提示，而是用
   「只输出一个 JSON 对象，键只能是……，不要新增字段/解释/代码块」重试一次；
2. **原始片段留档**：结构破损时把响应（截断 2KB）写进 `coverage.structure_failures`，
   否则这类失败事后是黑盒；
3. **闸门拆项**：新增 `structure_valid`，与引用问题分开；同时修正空字段时
   `has_citation` 还写"全部字段带来源"的假话，改为"各字段均无内容，未形成引用"。

### 第 4 次运行：结构重试生效，但覆盖判据本身不成立

| 项 | 第 3 次 | 第 4 次（加结构重试） |
|---|---|---|
| `uncovered_units` | `['d3','d4']` | **`[]`** |
| `flagged_units` | — | `['d2']` |
| `structure_failures` | 未记录 | **4 次**（原始片段已留档） |
| 陈述 | 67 | 64（54 支持 / 10 待审） |
| 输入 / 缓存 | 512k / 97% | 472k / 97% |
| 耗时 | 10m36s | 9m28s |

**结论一：结构重试有效。** 不再出现"整批字段被拒 → 该段零产出"，`uncovered_units` 归零；
4 次破损被重试救回，且原始响应留了档。

**结论二：我上一轮的"d3 漏读"判断站不住。** 本轮 d3 有产出（`uncovered` 为空），
但它的 13 块仍然 **0 引用**；同时 d2 的引用从 17 掉到 3。原因是 whole 模式**允许在任意章节取证**
（代码里明确写了"结论引用方法细节是正常的"），所以"某条指令的块没被引用"既可能是漏读，
也可能是模型从别处概括。

**因此不能再用"该指令的块是否被引用"当覆盖判据。** 两条可选口径：

1. **限定每指令的引用范围**——只准引用本节；代价是砍掉合法的跨节引用；
2. **改按章节问**：要求每条陈述带 `section` 标注，再看"每个章节是否至少有 N 条"；
   同时接受"块级覆盖率"作为参考值（本轮 59/152 ≈ 39%，对 21 页综述是正常量级）。

### 有界对话（bounded brief，2026-10-20）

实现：`extract.bounded_brief()`。第 N 条指令发出前，把前几条的**概要**附在指令末尾：

```
前文已提取的概要（仅用于保持术语与结论一致，**不得作为引用依据**；任何陈述仍必须引用原文标签）：
- d1（Introduction、Overview of RAG）：9 条，字段 研究问题、方法、结论
```

刻意**不回放原文与上一轮输出**：历史越长输入越贵、错误越容易传染，模型还会开始引用自己上一轮的句子。
概要里的"不得作为引用依据"是硬约束——引用仍要落到原文 `[P#]`，否则字段级校验会拦下。

尚未验证：需要一次真实整篇运行，对比「独立」与「有界对话」的重复陈述率、跨章矛盾数、引用可回溯率。

### 关于三次超时的更正

先前记录的"单次请求过大导致超时"**判断错误**，已作废。事实是：

- 同一路径、同一篇论文，把超时收到 90s 后 **1 分 48 秒就跑完**（3 次调用 19s/32s/54s）；
- 厂商后台显示所有成功调用都在 20–60s 返回；
- 三次失败是**个别请求被挂起**，客户端重试把一次挂起放大到 600s×N，才表现得像"卡了半小时"。

结论：超时是偶发挂起 + 重试策略的问题，**不是请求规模**；真正要改的是"一条指令承载多少陈述"的粒度。
